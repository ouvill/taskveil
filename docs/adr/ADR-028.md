# ADR-028: email ownership確認をOPAQUE登録前に行い、配送を独立Cloudflare Workerへ委譲する

**日付**: 2026-07-26
**状態**: Accepted（2026-07-26 プロダクトオーナー承認）

### 背景

Taskveilはemailをlogin aliasとして使うが、現行registrationは形式と重複だけを
確認し、mailbox ownership確認前にOPAQUE stateと永続account identifierを作成する。
第三者が他人のemailを先に登録でき、email変更もOPAQUE credential identifierと
E2EE password wrapperへ影響する。

Taskveilの認証・account・E2EE control planeの正本はAWS Lambda上のRust serverと
Postgresである。Cloudflare Email Serviceは2026-07時点でtransactional Email
SendingをPublic Betaとして提供し、Workersの`send_email` bindingから送信できる。
一方、既存realtime WorkerはPIIを持たない欠落可能なsync hint専用境界である。

email確認が証明するのはmailboxへのaccessであり、実在人物のidentity、OPAQUE
password、certified device、Recovery Key、E2EE plaintextへのaccessではない。

### 決定

1. registrationを`request → verify → OPAQUE start → OPAQUE finish`へ分割する。
   verification完了前はdurable user、tenant、device、sessionを作成しない。
2. `register/request`はnew、existing、内部throttle、provider suppressionを同じ
   `202 Accepted` response contractで扱う。known accountにも外部から区別できない
   decoy request lifecycleを割り当て、`register/request`、OTP verification、
   resend、expiry、`register/start`のstatus、body、
   error shape、概算処理時間、観測可能な状態遷移をaccount存在有無で分岐させない。
   IP/global abuse limitだけは、account存在と独立した同じ判定規則により
   `429 Too Many Requests`と`Retry-After`を返してよい。
3. verification secretはOS CSPRNGとrejection samplingで生成する8桁ASCII decimal
   OTPとする。NIST SP 800-63Aの6桁以上という下限より強い8桁を採用し、serverは
   `challenge_id`、generation、key versionへbindingしたHMAC-SHA-256 digestだけを
   保存する。OTPはsingle-use、10分expiry、1 challengeあたり最大5回の照合とし、
   上限はapplication判定だけでなくPostgresの`CHECK`と条件付き`UPDATE`でも強制する。
   resendがcommitした時点でgenerationを進め、旧OTPを即時失効する。
4. 確認は元のnative app内で完結させる。emailはOTPだけを含み、verification URL、
   browser page、fragment token、custom scheme、ticket pollingを使用しない。
   利用者が要求していない場合はemailを無視してよい旨を本文に明記する。passwordは
   OTP成功後に初めて入力・保持し、mailbox待機中のjournal、UI controller、非同期
   polling taskへ渡さない。
5. `register/request`時にclientは32 byteの`handoff_secret`を生成し、
   `S256(handoff_secret)`だけを送る。responseはaccount存在有無にかかわらず同形の
   opaque `request_id`を含む。元のappは`request_id`、`handoff_secret`、利用者が
   入力したOTPを一つのverification requestとしてPOSTする。serverはhandoff proofと
   OTPを同じrow lock下で照合し、reservation取得、verified遷移、ticket発行をatomicに
   行ってresponse bodyへ直接返す。verifyにも事前保存済み`Idempotency-Key`を必須とし、
   成功・generic rejectionの双方を同じtransactionで暗号化保存して、応答ロス後は
   同一tupleだけを再生する。clientはOTP入力へkeyed bindingしたverify keyをnetwork前に
   durable化し、同じ入力のretryでは維持し、別入力またはresend後の新generationでは
   rotateする。これにより応答ロスでattemptを二重消費せず、新しいOTPを旧rejectionへ
   誤ってbindingしない。
6. verification成功時に32 byteのopaque `registration_ticket`を一度だけ発行する。
   ticketはversion付きAEAD ciphertextとlookup用HMAC digestだけを保存し、5分expiry
   とする。`register/start`がticketをatomic consumeする。
   `register/start`のresponse lossに備えるidempotency resultは、
   `request/challenge ID`、purpose、canonical request hash、`Idempotency-Key`へ
   AEAD AADでbindingして暗号化保存し、5分以内かつ同じtupleに限り再生する。raw
   ticketをDBへ平文永続化せず、tupleの不一致、期限切れ、consume後の異なるrequestは
   同じgeneric error contractで拒否する。ticketからverified email、stable
   `opaque_credential_id`、purposeを復元し、client入力のemailをOPAQUE credential
   identifierとして信用しない。clientはremote `register/request`前にhandoff secret、
   server origin、完全なrequest body、request Idempotency-KeyをDevice Key保護済み
   領域へ保存する。ticket取得後もremote `register/start`前にOPAQUE client state、
   完全なstart body、start Idempotency-Keyを保存し、passwordは保存しない。remote
   `register/finish`前にはRecovery Key、local identity material、完全なfinish
   request、finish Idempotency-Keyを同領域へ確定する。serverは各mutationのresponseを
   同じtransactionでAWS-only keyringにより暗号化保存し、response loss後も同じrequest
   だけを再生する。start responseはserver-side replay deadlineを明示する。
   client journal遷移はcredential generation CASで行い、reservation取得前のrequest、
   OTP待機だけをcancel可能とする。verified以後は期限切れでreservationが解放されるまで、
   ghost accountと即時再登録のdecoy化を避けるためcancelを拒否する。
   remote finish結果と期待するuser/tenant/device identityをlocal journalへ先に保存し、
   profile、capsule、device identity、session credentialを各々存在確認付きで
   idempotentに確定する。session credentialは最後に公開する。期限切れ
   `PreparedFinish`は永続Busyにしない。clientは`request_id`、handoff proof、
   start/finish Idempotency-Keyで認証した`register/status`を使い、finish結果が
   commit済みなら24時間保持する暗号化receiptから同じsession結果を取得してlocal
   finalizeを再開する。未commitならjournalを安全に破棄して登録を最初から再開する。
   receipt失効でcommit有無を証明できない場合は、同じpasswordによるOPAQUE login成功に
   加えて、loginで復元したMK、account-root public key、Tenant Root DEKとgenerationが
   prepared registrationのlocal materialへconstant-time一致した場合だけlocal
   recoveryへ進む。既存account向けdecoy registration等で一致しないloginは通常の
   再認証として継続し、無関係なRecovery Keyをsessionへ帰属させずcrypto-shredする。
   generic login failureは未commitの根拠にせずjournalとRecovery Keyを保持し、
   再入力を許す。破棄が必要な場合もRecovery Keyを先に表示し、明示ack前は
   crypto-shredしない。
   Recovery KeyはOS保護領域の`RecoveryDisplayPending`に保持し、UI acknowledge後だけ
   crypto-shredする。remote commitが確定したactive sessionとreceipt失効後の
   commit-uncertain journalの双方で、再起動後も通常画面へ進む前に同じRecovery Key
   表示を再開する。refresh credentialが先に失効してもkey表示とackを可能にし、ack後は
   account-bound identity checkを維持した再認証画面へ遷移する。cancel/logoutは
   未acknowledged keyを暗黙破棄しない。
7. OPAQUE credential identifierはrandom stable UUIDとし、可変なemail login
   aliasから分離する。email変更はOPAQUE record、password-derived wrapper、
   Master Key、E2EE record identityを変更しない。既存のemail bytesへbinding
   されたOPAQUE recordはpasswordなしにUUIDへ安全に変換できないため、pre-release
   forward migrationで既存の開発用account graphをatomic resetし、再登録を求める。
   legacy email credential pathやdual readは残さない。
8. emailはoriginal/display値とcanonical lookup値を分けて保存する。初期版の受理
   grammarはASCII `dot-atom` local-partとIDNA domainからなる単一addr-specへ限定し、
   前後の空白だけを除去する。quoted local-part、domain literal、末尾dot、空label、
   CR/LF、control character、display name、comment、address list、EAI local-partは
   拒否する。local-partは64 ASCII octet以下、各A-labelは1〜63 octet、A-label化後の
   domainは253 octet以下、addr-spec全体は254 octet以下とする。domainはRust
   `idna` crate `=1.1.0`のUTS #46 non-transitional処理でA-label化してlowercase、
   local-partはcase-preservingかつexact comparisonとする。canonicalizationは
   serverの単一関数を正本とし、provider固有のdot除去、plus-address除去、暗黙case
   foldingは行わない。
9. challengeと`email_delivery_outbox`を同じPostgres transactionで作成する。
   `register/request`はcommit後にprovider応答を待たず同形の202を返す。outboxの
   recipient、OTP、template dataはversioned keyによるAEAD ciphertextとして
   保存し、lookup用DB列にはOTPのversion付きHMAC-SHA-256 digestだけを保存する。
   初期版はraw lifecycle eventを購読せずprovider acceptanceをAWS側で検証できない
   ため、ciphertextは`not_after`後に削除する。将来早期削除を行う場合は、
   `delivery_id`とprovider message IDだけを含む署名済みstatus callbackを別途設計し、
   recipientや本文をAWS側callbackへ戻さない。
   canonical email reservationは未確認request時には取得せず、verification
   transactionでcurrent/previous canonical digest候補を安定順序のadvisory lockにより
   直列化して取得する。account確定にはDB unique constraintを最終guardとして使用し、
   同じcanonical emailへの並行verification/finishは一つだけ成功させる。provider
   deliveryはcanonical digestとchallenge単位のdurable cooldownと有限budgetを持ち、
   抑止時もaccount存在と独立した同形202へ収束する。抑止requestは全体capacityには
   数えるがidentifier capacityを取得せず、既存の有効challengeを削除・置換しない。
   resend時にcapacityとdelivery budgetを取得できた場合だけatomicに昇格する。
   identifier capacityの昇格用`SECURITY DEFINER`関数は任意digestを受け取らず、
   実在challenge IDを`FOR UPDATE`でlockして、そのrowのstored digestと未claim状態だけを
   一度昇格する。runtime roleへcapacity counterの直接書込権限は与えない。
   request/resend responseはdurableな`next_retry_at`を返し、resendは
   Idempotency-Keyへbindingした暗号化responseを再生する。配送recipientは受理した
   case-preserving local-partとA-label domainを組み合わせる。
   verified reservationはticketと同じ5分で期限切れにし、start成功transactionで
   25分へ延長する。AWS-only state keyring、OTP/token HMAC keyring、Worker-shared
   delivery payload keyring、delivery signing key、dispatcher keyはすべて分離し、
   current/previousを跨いだ同一鍵値を起動時に拒否する。token keyを外す前はDBの
   旧version rowが0であることをruntime gateでも検証し、不整合時は新規登録を停止する。
10. 初期配送providerはCloudflare Email Serviceとする。既存realtime Workerへ
    混在させず、専用auth-email WorkerをPostgres outbox後段のdelivery adapterとして
    用意する。dispatcherはoutboxをclaimし、method、path、key ID、timestamp、
    body digestへbindingしたHMAC署名、stable
    `delivery_id = (challenge_id, generation)`、`not_after`付きcommandを再送する。
    Workerの2xxはQueueへのdurable enqueueだけを意味し、provider acceptanceや
    inbox deliveryを意味しない。
11. auth-email Workerは認証DBを持たず、account存在確認、OTP検証、ticket発行を
    行わない。8192 byteのbounded stream readerでcommandを読み、署名済みcommandを
    delivery ID単位のDurable Object ingress leaseを通してCloudflare Queueへenqueueし、
    consumerが
    `send_email` bindingで送信する。bindingはverification用senderだけを
    `allowed_sender_addresses`で許可する。送信command Queue bodyは`delivery_id`、
    `not_after`、version付きAEAD ciphertextだけとし、復号鍵をversion管理する。
    delivery ledgerはingress enqueueing/enqueuedとEmail Service sending/acceptedを
    独立状態として保持し、`not_after`にQueue retentionとclock marginを加えたalarmで
    `deleteAll`する。
    Cloudflare生成のlifecycle event Queueはrecipient、subject、SMTP response等の
    plaintext PIIを含む別境界であるため、初期版ではraw event subscriptionを
    有効化せず、provider dashboardの集計metricだけを利用する。将来購読する場合は
    command Queueと分離し、最短retention、log禁止、DLQ、access control、削除運用、
    data locationを別のsecurity reviewで承認する。
12. deliveryはat-least-onceであり、exactly-once送信を保証しない。consumerは
    stable `delivery_id`でbest-effort dedupeするが、同じOTPを含む重複mailは
    許容する。retryable errorだけを再試行し、terminal errorと`not_after`経過後は
    ackする。Queue retentionは1時間以下、OTPの`not_after`は10分以下とし、
    plaintext DLQを禁止する。resend後に遅延した旧generationのmailが届いても、
    verification APIは旧OTPを拒否する。`Retry-After`はRFC 9110のdelta-secondsと
    HTTP-dateを解釈し、provider試行前のlease deferはattempt budgetを消費しない。
13. sending domainはauth transactional専用subdomainとする。Cloudflare DNS上での
    domain onboarding、Workers Paid plan、sender allowlist、quotaを本番前に確認する。
    SPFとDKIMを有効化し、DMARCは観測用`p=none`から`quarantine`、`reject`へ段階的に
    強化する。新規sending domainで自動有効になるCloudflare Email Previewは
    verification OTPや本文を保存しないよう送信前に無効化し、設定driftをdeploy
    checklistまたは自動監査で検出する。Queue retentionはdefault値へ依存せず
    1時間を明示設定し、deploy時に検査する。
14. delivery telemetryは、Worker ingress accepted、Queue accepted、Email Service
    API acceptedと`messageId`取得、recipient MTA accepted
    （`message.delivered`）、deferred、bounced、rejected、complainedを別状態で扱う。
    `message.delivered`はrecipient MTAによる受理であり、inbox placementは観測不能
    とする。ownershipを成立させるのはhandoff proof付きOTPのPOSTだけであり、provider
    callbackではない。初期版はraw lifecycle eventを購読しないため、bounce、
    complaint、suppression、quota、provider failureの集計metricとprovider運用を
    監視する。recipient、subject、SMTP response、OTP、email bodyを
    application log、trace、analytics、Worker tailへ記録しない。Queue、DLQ、
    provider log、metadata/data-location境界もproduction review対象とする。
15. email変更はrecent OPAQUE reauthenticationとcertified-device proof、新email
    確認、旧emailへの通知を必須とする。account recoveryは別protocolとし、email
    だけでOPAQUE credential、device roster、E2EE key wrapperを置換できない。
16. Recovery Keyもcertified deviceも失った利用者について、supportまたはemail
    providerが旧E2EE contentを復旧する機能は提供しない。将来のrecovery設計でも
    email ownershipとE2EE key recoveryを独立要素として扱う。
17. Cloudflare Regional ServicesはHTTPS処理場所の制御であり、QueuesやEmail
    Serviceの保存場所を自動的に保証するものとは扱わない。production deploy前に
    contract、plan、Queue、Email Service、Preview、event metadataそれぞれの保存
    場所とretentionを確認し、Taskveilのdata-location要件へ適合しなければ
    provider-neutral adapterの別実装へ切り替える。この確認を推定やmarketing表現で
    代替せず、Cloudflare Data Localization Suiteが必要な場合はEnterprise契約を
    明示的な人間release gateとする。

### 帰結

- mailboxを所有しない第三者はdurable accountを確定できない。
- email変更がOPAQUE recordやE2EE key hierarchyを暗黙に変更しない。
- Postgres transactional outboxによりchallenge作成と配送要求のdual-writeを避ける。
- Cloudflare障害やBeta仕様変更はdelivery adapter内に閉じ、auth databaseの
  correctnessへ影響しない。Queueのat-least-once特性により同じmailが重複して
  届く可能性は残るが、OTPの効果はsingle-useである。
- registration endpoint、server schema、client/FRB/UI、Cloudflare Worker、
  infrastructureへbreaking changeが及ぶ。
- pre-release migrationで既存の開発用accountと紐づくserver ciphertextを削除する。
  migration前に保持すべき開発fixtureがある場合はRecovery Keyではなくtest seedから
  再生成し、実利用dataが存在する環境へはこのmigrationを適用しない。
- app内にOTP入力、再送期限表示、password入力、Recovery Key acknowledgeの段階UIが
  必要になる。
- production前にWorkers Paid plan、Cloudflare DNS/domain onboarding、sender
  allowlist、quota、Email Preview無効、Queue retention、SPF/DKIM/DMARC、
  data location、bounce/complaint運用を確認するrelease gateが増える。

### 却下した代替案

- **確認前にuserを作り`email_verified` flagだけを持つ案**: account squattingと
  orphan tenant/deviceを残し、確認前accountの権限制御が全routeへ広がる。
- **emailをOPAQUE credential identifierのまま使う案**: email変更がOPAQUE再登録と
  E2EE password wrapper更新を必要とし、可変aliasと安定credentialを混同する。
- **旧email credentialとstable UUID credentialを併存させる案**: account存在や
  migration状態による分岐を認証境界へ恒久化し、pre-releaseで不要なdowngrade面を
  残すため採用しない。
- **verification tokenをJWTにする案**: DB lookupを減らせるが、single-use、
  resend invalidation、purpose binding、emergency revocationを別stateなしに
  強制できない。
- **既存realtime Workerへemail送信を追加する案**: PIIを持たない欠落可能hint境界へ
  auth tokenとrecipientを持ち込み、failure/retention特性が異なる責務を混在させる。
- **Postgres outboxを持たずAWS LambdaからWorkerへ同期送信する案**: challenge作成と
  配送要求がdual-writeになり、片方だけ成功する障害を閉じられない。
- **outbox dispatcherからCloudflare Email REST APIを直接呼ぶ案**: hopは少ないが、
  provider token、template、delivery eventをAWS側へ持ち込み、Workers bindingに
  よる隔離を失う。auth-email Workerの追加retry層やPII運用が成立しない場合の
  fallback adapterとしては温存する。
- **高entropy linkをbrowserで確認してappがpollする案**: URL・browser history・
  referrer・cross-device handoffの境界が増え、元アプリがpasswordを保持したまま
  待機する実装を誘発する。8桁OTP、10分期限、5回上限、handoff proofの組合せで
  online guessingをDB制約付きで制限できるため不採用。
- **provider固有のGmail canonicalizationを行う案**: RFC上異なるmailboxを誤って
  統合し得るため採用しない。
