# ADR-027: 共有local profileを階層lock・runtime epoch・fenced leaseで調停する

**日付**: 2026-07-26
**状態**: Accepted（2026-07-26 ユーザー明示承認）

### 背景

ADR-011は、同一PC上のFlutter desktop、CLI、MCP serverが同じlocal profileを
共有する方針を採用し、SQLiteの短いtransactionとDB-backed sync leaseを要求した。
しかし、`TaskveilClient`のruntime stateとsync single-flightはinstance内に閉じている。
SQLiteのwriter lockはDB rowの原子性を守るが、OS secret store、cached account /
crypto state、Device Key capsule、network requestを含むworkflow全体は守らない。

そのため別instanceは、account bind後も古い`Anonymous` stateでoutboxを作らずdomain rowを
更新し、Device Key rotation後も旧DB keyを保持し得る。別processのsync runも同時に
network side effectを開始できる。PID fileまたはSQLite busy timeoutだけでは、
process crash、PID再利用、network待ち、stale owner takeoverを安全に扱えない。

本ADRはADR-011の共有方針、OS secret store、物理DB共有範囲を維持する。一方、
ADR-011の決定9・10とその帰結にあるprocess間coordinationの運用詳細は本ADRで具体化し、
両者が競合する場合は本ADRを優先する。

### 決定

1. process間coordinationはfrontend adapterでなく`taskveil-client`が所有する。
   Flutter bridge、CLI、MCPはlock、lease、repository、DB keyを直接保持しない。
2. local profileの同一性は、作成後にcanonicalizeしたprofile directoryから決め、
   DB pathはその配下の固定名とする。相対path、symlink / junction、Windowsのcase差で
   別profileとしてlockを迂回できないようにする。生pathはlog、error、owner metadataへ
   出さない。`TaskveilClient`はopen時のdirectory identityとDB identityをprocess
   lifetime中保持し、guard取得後にもpathnameが同じidentityを指すことを検証する。
   identity driftは`ProfileLockUnsupported`としてfail closedにする。Windowsでは
   profile root handleをclient lifetime中保持してdelete / rename sharingを拒否する。
   rootだけでなく既存のprofile lock、session lock、DBもhandleからownerとDACLを検証し、
   継承を無効化したchildや移入済みfileにuntrusted write権限があれば拒否する。
   Unixでは同じ実効UID、mobileでは同じapp container / App Groupをtrusted boundaryとし、
   group / world writableなrootまたはDBを拒否する。権限を持つ悪意あるsame-UID processに
   よるrename、unlink、ptrace等への防御は本coordination契約の対象外とする。
3. lock取得順序を次に固定する。
   1. canonical profile identityで共有するprocess-local coordinator registryの
      shared / exclusive guard
   2. profile directory内のlock handleによるOS advisory shared / exclusive guard
   3. session credential lockまたはDB-backed sync lease
   4. SQLite transaction
4. SQLite transaction内から上位lockを取得しない。network request中はSQLite transactionを
   保持しない。通常read / local mutationはprofile shared guardを使う。syncは短いshared
   guard内でcapsule / runtimeを再検証してDB keyとruntime epochをsnapshotし、network
   await前にguardを解放する。以後はDB-backed lease / fencingを正本とし、Tenant key
   cutoverでもlease保持中にprofile guardを再取得しない。cutoverはfenced transactionと
   post-commitのruntime epoch CASでstale publicationをfail closedにする。migration、
   account/device bindingを変更するauth / logout、Device Key rotationとcrash recoveryは
   profile exclusive guardを使う。
5. `TaskveilClient::open`はexclusive guard内でcapsule recovery、SQLCipher open、
   migration、runtime loadを行う。通常operationへ移るときにexclusiveからsharedへ
   原子的に移行できないOSでは、guard再取得後にepoch、capsule、migration ledgerを
   再検証してからruntimeを公開する。
6. OS advisory lockがprofile間排他の正本である。lockfileの存在、PID、owner metadataは
   排他判定に使わない。process crash時はkernelによるhandle解放で回復し、
   staleに見えるlockfileを削除してunlockしない。child processへlock handleを
   意図せず継承させない。同一processではcoordinatorが1本のhandleを保持し、
   reader countの0→1でshared lock、1→0でunlockすることで、platformごとの
   複数handle close semanticsへ依存しない。
7. macOS / iOSはplatformが提供するadvisory file lock、Windowsは`LockFileEx`相当、
   Linux / Androidは`flock`または`fcntl`相当を用いる。productionで安全なlock、
   canonical identity、secret storeのいずれかを利用できない場合は
   `ProfileLockUnsupported`としてfail closedにし、SQLite-onlyまたは平文storeへ
   降格しない。
8. iOS / Androidとdesktopが同じ物理profileを共有することはADR-011どおり対象外とする。
   ただしmobile appの別process、background service、App Extensionが同じapp container /
   App Group profileを開く場合は同じcoordination契約を適用する。同一processのisolate /
   taskはprocess-local coordinatorへ収束させる。
9. SQLCipherへprofile bindingと単調な`runtime_epoch`を永続化する。account/device binding、
   Tenant Root Key cacheの実質的変更は、binding/cacheを発行する同じ`IMMEDIATE`
   transactionで`runtime_epoch`をchecked incrementする。device再束縛はruntime発行前に
   local HLC、quarantineを含む全outbox headとaccount device markerを原子的に更新する。
   Tenant Root Keyの同一性はrandomized AEAD ciphertextのbyte列では判定せず、既存cacheを
   Master Keyで認証付き復号したgenerationごとのkey materialと比較する。同generation・
   同keyは既存ciphertextを保持してno-op、同generation・異keyはfail closedとする。
   serverがactive / migration中として返すgeneration集合を正本とし、各generationを
   MK-wrapped rowとして保持してprocess再起動後もmigration中のhistorical recordを
   復号できるようにする。remote集合からretireされたgenerationは同じtransactionで削除し、
   その削除も実質的cache変更としてepochを更新する。
   overflow時はwrapせずprofile変更を拒否する。
10. active Device Key capsuleは非秘密のgeneration markerを持つ。各clientは
    `loaded_epoch`とloaded capsule generationを保持し、operation開始時とcommit前に
    durable stateを再検証する。不一致時はtransactionを開始しないかrollbackし、
    exclusive変更完了後にDB connection、DB key、account / crypto runtimeを再読込する。
    一度の再読込で整合しなければfail closedにする。
11. secret storeとSQLiteは単一transactionにできないため、credential publicationと
    Device Key rotationはpending / active markerを持つdurable sagaとする。
    exclusive guard内で既存のactive / pending recoveryを完了し、途中状態のまま通常operationを
    再開しない。process crash後はOS lock解放、SQLite rollback、pending recoveryにより
    手動修復なしで収束させる。
12. sync runはSQLCipher内の単一row leaseを使う。leaseはランダムowner ID、expiry、
    checked incrementするfencing token、取得時runtime epochを持つ。acquire / renew /
    releaseは短い`IMMEDIATE` transactionで行い、有効な別ownerがいる場合は
    `SyncLeaseBusy`を返す。
13. network request timeoutより長いTTLを用い、各write transactionの開始前にleaseを
    renewする。leaseを更新できない、expiryを超えた、runtime epochが変わった、
    別ownerがtakeoverした場合はstorage内部の`SyncLeaseLost`（公開時は`LeaseLost`）とし、
    以後のnetwork requestを開始しない。同じrunが新epochでleaseを取り直すことは禁止し、
    outer operationを終了してprofile runtimeとsync contextを再解決した新runだけが取得する。
    sync中のTenant Root Key refresh自身がepochを変更した場合も、そのrunは新keyを使って
    続行せず`LeaseLost`で終了し、次のrunでcontextを再構築する。
    response受信後のACK、cursor、pull apply、full-resync stateの各transactionはowner、
    fence、runtime epochが一致する場合だけcommitする。
14. local fencing tokenは、既に送信したHTTP requestをserver側で取り消さない。
    remote side effectは既存の`op_id`、base revision CAS、冪等ACKにより再送安全にする。
    server-side fencingが必要になった場合は別のwire / server schema ADRで裁定する。
15. error taxonomyを少なくとも`ProfileBusy`、`SyncLeaseBusy`、`LeaseLost`、
    `ProfileLockUnsupported`、`DatabaseBusy`へ分ける。runtime epoch不一致と
    capsule generation変更は通常は内部reload条件とし、秘密、credential、復号内容、
    生profile pathをerrorまたはlogへ含めない。
16. correctness検証は同一processの2 instance testだけで完了扱いにしない。
    barrierで同期した実child processにより、同時mutation / sync、stale runtime、
    lease expiry / takeover、強制終了後の回復、path alias、異なるprofileの並行性を
    desktop全対象OSで検証する。mobileで別process共有を有効にする場合は、
    platform instrumentation testもrelease gateとする。
17. CLI / MCPのshared profile実接続は、対象desktop OSのsecret store、OS lock、
    crash recovery、実process testが完了するまでreleaseしない。

### 帰結

- SQLiteは短いtransactionとmigration ledgerの正本を維持し、workflow排他は
  `taskveil-client`のprofile coordinatorが担う。
- local mutation同士はshared guard下でSQLiteにより短く直列化でき、長いsync network待ちは
  profile guardを保持しないためlocal CRUDと短いexclusive cutoverを停止させない。
  auth、migration、rotationがruntime epochを変更した場合、進行中syncは次のHTTP / commit
  boundaryで`LeaseLost`となる。
- 各operationでruntime epochとcapsule generationを再検証する費用が増えるが、
  stale runtimeによるoutbox欠落、旧key利用、旧device node pushを防げる。
- crashしたOS lock ownerは即時解放されるが、sync leaseはexpiryまで取得できない場合がある。
  takeover後はfencing tokenにより旧ownerのlocal commitを拒否する。
- desktop frontendは同じDBを直接開き続けられる。将来、常駐daemon / brokerへ移行する場合も、
  runtime epoch、fencing、crash recoveryはbroker所有profileの内部不変条件として再利用できる。

### 却下した代替案

- **SQLiteのWAL / busy timeoutだけに依存する案**: DB transaction外のcached runtime、
  secret store、rotation、network side effectを調停できない。
- **process lifetime中ずっとexclusive profile lockを保持する案**: 実装は単純だが、
  Flutter、CLI、MCPの同一profile共有とoffline並行read / mutationを実質的に禁止する。
- **PID fileまたはlockfileの存在で排他する案**: crash後のstale file、PID再利用、
  TOCTOUを安全に扱えない。
- **wall clock leaseだけで同期を守る案**: clock rollback、停止したowner、
  expiry直前に始めたoperationを識別できず、stale commitを拒否できない。
- **network待ちの間SQLite write transactionを保持する案**: local mutationとmigrationを
  長時間blockし、crash / retry時のlock競合を拡大する。
- **最初から常駐desktop daemonへ一本化する案**: 単一owner化は明快だが、
  CLIのoffline独立動作と配布・lifecycle要件を変更する。必要になった時点で別ADRとする。
- **OS lockがない環境でSQLite-onlyへfallbackする案**: P0の安全性を環境依存で失い、
  同じrelease binaryのprofile整合性契約を変えるため不採用とする。
