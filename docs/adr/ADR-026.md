# ADR-026: local DB migrationは不変SQLとchecksum ledgerで前方適用する

**日付**: 2026-07-26
**状態**: Accepted（2026-07-26 プロダクトオーナー承認）

### 背景

local SQLCipher DBは`PRAGMA user_version`と`core/storage`内のRust callback配列でv1からv22までを管理してきた。この方式は順次適用とtransaction rollbackを提供する一方、適用済みmigrationの内容をDB側で検証せず、schema変更の正本が単一のSQL fileになっていない。

server側はSQLx `Migrator`により、version付きSQL file、checksum ledger、前方適用を採用した。client側は同期的な`rusqlite` repositoryとbundled SQLCipherを使用しており、SQLx SQLite driverへの置換はnative SQLite link、async実行、全repositoryの接続型へ不要な変更を広げる。

Taskveilは一般配布前であり、既存の開発profileとlocal schema履歴を互換維持する必要はない。

### 決定

1. local DB migrationの正本は`core/storage/migrations/`に置くversion付きの不変SQL fileとする。適用済みfileを変更せず、修正は新しい前方migrationへ追加する。
2. `rusqlite`とbundled SQLCipherを維持し、SQLx SQLite driverは導入しない。migration runnerはSQLx相当のversion、description、checksum検証を`core/storage`内で提供する。
3. SQLCipher keyとconnection設定を適用した後だけmigration ledgerを読み書きする。
4. DB内のmigration ledgerはversion、name、checksum、applied timestampを保持する。ledgerをschema versionの唯一の正本とし、`PRAGMA user_version`は使用しない。
5. runnerは適用済みversionの連続性、name、checksum、repositoryにない未知versionを検証する。不一致時はDBを変更せず、incompatible schemaとして起動を拒否する。
6. 各migration SQLと対応するledger rowは同じ`IMMEDIATE` transactionで確定する。lock取得後にledgerを再検証し、Flutter / CLI / MCPの複数processが同じprofileを開く場合も同じmigrationを重複適用しない。
7. migrationはcompile timeにclient binaryへ埋め込み、実行時filesystemやnetworkから取得しない。
8. 現行v22の完成schemaを新しいv1 initial migrationへsquashし、旧v1〜v22 callbackと開発DB互換を削除する。既存開発profileは再作成する。
9. down migrationは提供しない。新しいschemaを知らない古いclientはDBを開かず、修正は新しいclientと前方migrationで行う。
10. 大規模なデータ変換で別DBへのcopy-and-swapが必要になった場合も、開始条件と完了markerをversion付きmigration契約として管理し、通常runnerを迂回する暗黙のschema修復は行わない。

### 帰結

- serverとclientで、不変SQL、checksum検証、前方適用という運用規律が一致する。
- client repositoryは同期的な`rusqlite::Connection`を維持し、SQLCipherのbuild・鍵設定経路を一本化できる。
- migration fileの誤編集や欠落は既存profileを暗黙に異なるschemaとして扱わず、起動時に検出される。
- 一般配布後にrunnerを変更する場合は、旧ledgerを検証して新ledgerへ移すbridge migrationが必要になる。

### 却下した代替案

- **SQLx SQLite driverをclientへ導入する案**: serverと同じlibraryを使えるが、`rusqlite` / `libsqlite3-sys` / SQLCipher linkと同期APIへ変更が広がり、migration管理だけの利益に対して負担が大きい。
- **`PRAGMA user_version`だけを継続する案**: 単純で高速だが、適用済みmigrationのnameとchecksumを検証できない。
- **Refineryを導入する案**: 求めるledger機能に近いが、採用時点のreleaseはTaskveilが固定する`rusqlite 0.40.1`を受け付けない。
- **`rusqlite_migration`を導入する案**: 現行`rusqlite`と互換であるが、状態管理が`PRAGMA user_version`でchecksum ledgerを持たず、本決定の整合性要件を満たさない。
- **起動時に期待schemaへ自動reconcileする案**: migration履歴とデータ変換順序が不明確になり、端末ごとの結果を監査・再現できない。
