# ADR-025: OPAQUEの後段を短命access tokenとローテーション式refresh tokenで管理する

**日付**: 2026-07-25
**状態**: Accepted（2026-07-25 プロダクトオーナー承認）

### 背景

TaskveilのOPAQUE認証は、serverへpasswordを渡さず本人確認を行うだけでなく、端末が`export_key`からMaster Keyを解除する役割を持つ。このため外部browserで完結する一般的なOIDC Authorization Code flowへそのまま移すと、native appが必要とする`export_key`を安全に受け取れない。

一方、OPAQUE完了後に発行する30日有効の単一opaque bearer tokenには、権限を限定した短命token、継続利用用credentialのrotation、credential theftの再利用検知、標準的な失効endpointがない。特殊性が必要なのはE2EE鍵解除を伴う認証部分であり、認証後のAPI session lifecycleまで独自にする必要はない。

### 決定

1. OPAQUEはnative appとTaskveil server間の認証、および端末内のMaster Key解除に使用し続ける。`export_key`は端末外へ出さず、session tokenの導出やserver認可には使用しない。
2. OPAQUE登録・login完了後、serverは暗号学的乱数からopaque access tokenとopaque refresh tokenを発行する。DBへは各tokenのSHA-256 hashだけを保存する。
3. access tokenはBearer tokenとしてresource endpointへ送り、有効期間を最大15分かつsession family absolute期限以内とする。serverはtoken、session family、device certificate、device key期限、tenant membershipをrequestごとに検証する。
4. refresh tokenはmobile public client専用のtoken endpointだけへ送り、有効期間を最終利用から30日、session familyのabsolute lifetimeを90日とする。client IDは`taskveil-native`に固定し、client secretは持たせない。
5. refresh成功は同一transaction内で旧refresh tokenを消費済みにし、次世代refresh tokenと新しいaccess tokenを発行する。refresh tokenは一度だけ利用できる。
6. 消費済みrefresh tokenが再提示された場合、漏えいしたtokenと正規clientのどちらが再利用したか判別できないため、同じsession familyのaccess tokenとrefresh tokenをすべて失効する。grace windowと過去responseの再配布は行わず、応答喪失時は再loginするfail-closed設計とする。
7. 明示的失効はRFC 7009互換のrevocation endpointで行う。refresh tokenの失効はfamily rowだけをO(1)で失効して配下tokenを即時無効化し、access tokenの失効はそのtoken rowだけを対象とする。familyの子rowへ無制限fan-out UPDATEを行わず、後段のbounded GCで回収する。token probingを防ぐため、未知または既に失効したtokenにも200を返す。
8. RFC 8414互換のAuthorization Server metadataでissuer、token endpoint、revocation endpoint、`refresh_token` grant、client authentication method `none`を公開する。OPAQUE start / finish APIはTaskveil固有のfirst-party認証APIであり、OAuth authorization endpointとは表現しない。
9. access token、refresh token、各期限、発行元兼resource originはversion付きの単一token setとしてOS安全領域へ保存する。originはHTTPSのscheme / host / portだけへ正規化し、localhost / loopbackの開発環境だけHTTPを許す。refresh、resource request、revokeは可変な設定値ではなくtoken setに束縛されたoriginへだけ送る。activeまたはpending credentialがある間は異なるoriginへの設定変更と再認証を拒否する。AppleはData Protection Keychain、Android releaseはKeystoreで保護されたstorageを使い、productionで平文fileへfallbackしない。
10. clientはaccess token期限の60秒前にrefreshする。register / loginによるcredential新規保存、refreshのload / HTTP交換 / 置換、logoutのrevoke / 削除、起動・期限切れ時の読込 / 削除を、同一local profileのcross-process advisory lockで直列化する。logoutはonlineでremote revocationが200となった後だけlocal credentialを削除し、network / timeout / 非2xxではcredentialを保持して失敗を返す。別processがsession credentialを更新中なら旧refresh tokenを送信せず一時的なbusyとして扱う。長時間実行されるsync / realtime resource requestが401となった場合は強制refreshして、その操作を一度だけ再試行する。refresh失敗、family失効、refresh期限切れではremote sessionをlogged-outへ遷移させるが、ADR-013どおりlocal crypto contextとoffline dataは削除しない。
11. DPoPは導入しない。access tokenはbearerであり窃取時のreplay耐性を持たないため、短命化、安全領域保存、TLS、ログ禁止、refresh rotation、端末・membershipのrequest-time検証でriskを制限する。sender-constrained tokenが必要になった時点で別ADRにより再評価する。
12. 一般配布前のため、旧30日session table、`session_token` response、logout endpointとのdual read / writeは行わず、新しいsession lifecycleへ一括置換する。
13. consumed refresh tokenはreuse検知のためfamily absolute lifetime中は保持する。serverless runtimeで常駐schedulerを前提にせず、認証・refresh request時に期限切れaccess token、absolute期限切れfamily配下のaccess / refresh token、空になったfamily、期限切れprovisional device、期限切れOPAQUE stateを段階的な固定上限batchで回収する。未認証request一件へ無制限DELETE、UPDATE、外部キーcascadeを負わせない。
14. login finish後のdeviceはprovisionalとする。certificateと`certified_at`が揃うまでresource認可、refresh、active roster、key recipient、rotation ACK対象に含めない。clientは認証済みuser / tenantを既存local profileへ照合し、token setのorigin、device秘密identity、enrollment proof、復号済みkey materialを`pending_device_certification`としてOS安全領域へ耐久保存してからdevice certifyを行う。certifyは同一certificateの再送を冪等に扱い、成功後のlocal finalizeでactive token setを最後に公開する。crashやlocal保存失敗時はpendingから再開し、profile不一致または未認証challenge期限切れではcertifyせずrefresh tokenをremote revokeしてからpendingを破棄する。server response受領前後でclientが停止してlocal pendingを持てない場合も、provisional deviceはactive stateへ影響せずchallenge期限後にbounded cleanupされる。

### 帰結

- OPAQUEとE2EE鍵解除の特性を維持しつつ、長期session credentialのrotation、reuse検知、明示失効を標準仕様に寄せられる。
- resource serverへ送るcredentialの露出時間は30日から15分へ短縮される。
- public clientに保存されたrefresh tokenが盗まれた場合、攻撃者または正規clientによる次の再利用でfamilyを閉じられる。
- refresh response受信後、token set保存前にprocessが停止すると再loginが必要になる。安全側に倒すため、この可用性上のtrade-offを受け入れる。
- DPoPを導入しないため、access token単体を窃取した攻撃者は最大15分replayできる。
- OAuth authorization endpointを提供しないため、本決定はOIDC provider化や第三者OAuth client対応を意味しない。

### 却下した代替案

- **外部browserのOIDC Authorization Code + PKCEへOPAQUEを内包する案**: browser側のOPAQUE `export_key`をnative appへ安全かつ標準的に戻せず、E2EE鍵解除の境界を複雑にするため不採用。
- **30日有効の単一opaque tokenを維持する案**: resource credential窃取時の有効期間が長く、rotationとreuse検知を持てないため不採用。
- **JWT access token案**: request-timeのdevice、membership、revocation検証が必要であり、自己完結tokenの利点よりkey rotation、claim設計、失効運用が増えるため不採用。
- **DPoPを同時導入する案**: bearer replay耐性は向上するが、端末key lifecycle、proof生成、nonce、clock skew、proxy/header処理、障害解析の実装・運用負荷が現段階では大きいため見送る。
- **refresh tokenのgrace window案**: network retryと窃取token再利用を区別できず、再利用検知の意味を弱めるため不採用。
