## 1. 技術スタック選定

### 1.1 全体構成

本アプリケーションは、クライアントUIとコアロジックを明確に分離した「Flutter + Rust」構成を採用する。

| レイヤー | 技術 | 役割 |
|---|---|---|
| クライアントUI | Flutter | iOS / Android / Windows / macOS / Linux 向けUI描画、ユーザー操作 |
| コアロジック | Rust | 暗号処理、同期エンジン、ドメインロジック、ローカルDBアクセス |
| ブリッジ | flutter_rust_bridge | Flutter(Dart) ↔ Rust のFFI境界を自動生成 |
| サーバー | Rust (axum) on AWS Lambda | OPAQUE認証、テナントプロビジョニング、同期API（push/pull）提供、課金Webhook（サーバーレス・常駐プロセスなし） |
| CLI | Rust (clap) | コマンドラインからのタスク操作 |
| MCPサーバー | Rust (rmcp 公式SDK) | LLMエージェント向けTodo操作インターフェース |
| ローカルAI | llama.cpp系Rustバインディング / candle | オンデバイス推論（自然言語パース、要約等） |
| 課金 | App Store / Play IAP、外部課金プロバイダ（Desktop / Org） | サブスクリプション課金 |

### 1.2 選定理由

- **Flutter**: 単一コードベースでモバイル・デスクトップの全対象OSをカバーでき、UI実装の生産性が高い。マテリアル/Cupertino双方の表現力があり、Todoアプリのような情報密度が高いUIとの親和性も良い。
- **Rust**: 暗号ライブラリ（鍵導出・AEAD・OPAQUE等）のエコシステムが充実しており、メモリ安全性の観点からもE2EEの実装言語として妥当である。加えて、コアロジックをRust crateとして切り出すことで、CLI・MCPサーバー・（将来的な）サーバーサイド機能から同一の暗号/ドメインロジックを再利用でき、実装の重複と検証対象の増加を避けられる。
- **flutter_rust_bridge**: DartとRust間の型安全なバインディングをコード生成できるため、手書きFFIに比べて保守コストが低い。

### 1.3 Flutter + Rust構成の評価

**妥当性の結論**: UIの生産性・クロスプラットフォーム性（Flutter）と、暗号実装の安全性・コアロジックのCLI/MCPへの再利用性（Rust）を両立できる構成であり、本アプリの要件（マルチプラットフォームE2EEアプリ、かつCLI/MCPを同一データストアに対して提供）に対して妥当と判断する。

**懸念点と対策**:

| 懸念点 | 内容 | 対策 |
|---|---|---|
| ブリッジのビルド複雑性 | flutter_rust_bridgeはRustのクロスコンパイル設定（iOS/Android/各デスクトップOS向けターゲット）をFlutterのビルドパイプラインに統合する必要があり、CI構築コストが高い | プラットフォームごとのビルドスクリプトをmonorepo内に集約し、CIでプラットフォーム別ジョブをキャッシュ付きで並列実行する。`cargokit` 等の既存の統合ツールチェーンの採用を検討する |
| Flutter Desktop（特にLinux）の成熟度 | プラグインエコシステムやネイティブ連携（キーチェーン、通知）がモバイルに比べて発展途上 | Desktop向けの重要機能（キーチェーンアクセス等）はRust側で自前実装し、Flutterプラグインへの依存を最小化する。Linux版は正式リリース時点でモバイル・Windows/macOSに対し機能段階（フィーチャーパリティ）が遅れる可能性を許容する |
| FFI境界でのエラーハンドリング | Rust側のpanicやエラーがDart側に正しく伝播しない場合、UIがクラッシュ/フリーズするリスク | Rustコア関数はすべて `Result` 型で返却し、`catch_unwind` でpanicを捕捉してDart側に構造化エラーとして通知する |

### 1.4 国際化（i18n）方針

顧客ターゲットはグローバルであり（[`01_企画書.md`](./01_企画書.md) §3）、初期リリースの時点から多言語対応を行う（[`02_機能仕様書.md`](./02_機能仕様書.md) F-48）。技術面の方針は以下のとおりとする。

- 基準言語は英語とする。全UI文字列はFlutter標準のl10nツールチェーン（ARBファイル + `intl`、ICU MessageFormat）で外部化し、UI層でのハードコードを禁止する。
- Rustコア側はエラー等を自然言語文字列ではなくエラーコードとして返却し、表示文言への変換はFlutter側のl10n層で行う。コア層に自然言語文字列を持たせない。
- CLI / MCPサーバーのメッセージは英語を基準とする（MCPのtool説明等も英語で記述する）。
- 日付・時刻・数値の書式化はロケールに従う。タイムゾーンは内部的にUTCで保持し、表示時にロケール・端末タイムゾーンへ変換する（§3のデータモデルと整合させる）。
- RTLレイアウトは、Flutter標準のRTLサポートを前提として初期実装の時点から考慮する。

### 1.5 サーバー実行基盤（決定: AWS Lambda）

サーバー（コントロールプレーン）は **AWS Lambda 上で Rust ネイティブバイナリとして稼働**させる。デプロイ形態は**コンテナイメージ + AWS Lambda Web Adapter（LWA）**とする。axum アプリケーションは通常のHTTPサーバーとして実装し（**Lambda 固有コードを一切含まない**）、静的バイナリと LWA を同梱した最小コンテナイメージ（distroless 等）として Lambda のコンテナイメージサポートでデプロイする。LWA が Lambda イベントとHTTPリクエストの変換を担う。常駐サーバーは持たない。

本節および6章の同期プロトコルに関する設計判断の経緯は [`05_設計判断記録.md`](./05_設計判断記録.md)（ADR-002・ADR-003）を参照。

**選定理由**（比較対象: Cloudflare Workers / Cloudflare Containers。2026年7月時点の調査に基づく）

1. **Rustネイティブ実行**: opaque-ke 等の暗号クレートを WASM 変換なしでそのまま利用できる。認証コードをWASM化の不確実性に載せない（Workersはworkers-rsによるWASM変換が必要でPoCを要する）。
2. **バイナリサイズ制約がない**: Workersはスクリプトサイズ上限（圧縮後、Paidで10MB）があり暗号ライブラリ入りWASMは圧迫しやすい。Lambdaはzipで250MB（展開後）、コンテナイメージなら10GBまで。
3. **データストアとの近接性**: サーバーレスPostgres（Neon等）はリージョン単位で稼働しており、Lambdaを同一リージョンに配置することでサーバー⇄Postgres間がリージョン内通信になり、同期API・認証APIのレイテンシと転送コストを抑えられる。
4. **可搬性**: アプリは Lambda 固有コードを含まない通常のHTTPサーバーであるため、**同一コンテナイメージ**を ECS / Fly.io 等へそのまま移設可能で、出口戦略が確保される。
5. **コールドスタート**: Rustの最小コンテナイメージ構成でのコールドスタートは概ね100〜300ms程度で、ログイン・トークン更新という低頻度APIのp99への影響は許容範囲。将来コールドスタート短縮が必要になった場合は、`lambda_http` + cargo-lambda による zip デプロイ方式（数十ms、ただし main 関数に Lambda 固有のエントリポイントが必要）への切替を検討する。

**不採用理由の要約**: Cloudflare Workers は WASM 制約・サイズ上限が課題。Cloudflare Containers（2026年4月GA）は任意のDockerイメージが動くもののコールドスタート1〜3秒・オートスケール未実装で、まばらな認証トラフィックとの相性が悪い（公式推奨もリソース集約型ワークロード向け）。

**周辺構成**: OPAQUEログインの多段プロトコルの中間状態は、DynamoDBではなく**同一Postgres内のephemeralテーブル**（`expires_at` カラムを持ち、状態消費（consume）時に該当行を即時削除するのに加え、定期クリーンアップジョブで期限切れ行を掃除する。OPAQUE中間状態は一度使用したら破棄する性質のものであり、DynamoDB等のネイティブTTL機構は不要である）に短期保存する。永続メタデータ（users/devices/ラップ済み鍵/organizations/subscriptions等）も同一Postgresに保存する（[`05_設計判断記録.md`](./05_設計判断記録.md) ADR-003を参照）。定期処理（tombstone GC・sync_records_historyの期限切れ削除・期限切れOPAQUE中間状態の掃除・失効後180日削除）は EventBridge Scheduler で実行する。tombstone GCは、`delete_hlc IS NOT NULL`かつ`encrypted_blob IS NULL`のtagged tombstoneを180日保持した後に削除し、テナントごとに `gc_horizon_seq` を記録する（2026-07-10改訂: ADR-010、ADR-014）。公開エンドポイントの前段は CloudFront + WAF または API Gateway のスロットリング（最終構成は§12未決事項）とする。ビルド・デプロイは Docker イメージビルド（linux/arm64 または x86_64）→ ECR push → Lambda 更新のパイプラインを CI に構築する。サーバーレスPostgresは**Neon**を採用し、初期リージョンは**eu-central-1（フランクフルト）**、Lambdaも同一リージョンに配置する（[`05_設計判断記録.md`](./05_設計判断記録.md) ADR-008参照）。接続はNeon組み込みの接続プーラー経由のTCP接続（sqlx）とし、Lambdaの同時実行数増加に伴うコネクション枯渇を回避する。プーラーはトランザクションモードで動作するため、セッション依存機能（advisory lock、LISTEN/NOTIFY等）は使用しない設計とする（本仕様は行ロックと通常トランザクションのみを用いており抵触しない）。

2026-07-19のADR-022により、上記の未決だった前段構成は**API Gateway HTTP API**に確定した。default 20 RPS / burst 40、認証route 5 RPS / burst 10で制限する。deployは同一commit SHAからx86_64 imageとWorkerを作成し、ECR digest固定、migration専用binary実行、Lambda version発行、alias切替の順とする。

Lambda runtimeはSecrets Managerのruntime secret ID、課金環境、公開issuer `TASKVEIL_AUTH_ISSUER`だけを環境変数で受け取り、AWS Parameters and Secrets Lambda Extensionからtyped JSONを取得する。JSONにはpooled non-owner `DATABASE_URL`、選択中のRevenueCat環境、realtime設定だけを含める。staging deploymentは`TASKVEIL_BILLING_ENVIRONMENT=sandbox`、production deploymentは`production`とし、非選択環境のRevenueCat secretを保持・読込しない。migration owner接続は別secretと`taskveil-migrate`専用とし、通常serverへ渡さない。`GET /health`はprocess livenessのみ、`GET /ready`はruntime DBへ`SELECT 1`を行い、失敗時も接続情報を返さない。

## 2. リポジトリ/モジュール構成

monorepo構成とし、以下のディレクトリ構成を基本とする。

```
taskveil/
├── app/                  Flutter アプリ本体
│   ├── lib/
│   ├── ios/ android/ windows/ macos/ linux/
│   └── rust_builder/     flutter_rust_bridge 生成物・ビルド設定
│
├── core/                 Rust コアクレート群
│   ├── domain/           エンティティ・ユースケース（純粋ロジック）
│   ├── crypto/           鍵導出・暗号化・OPAQUE クライアント実装
│   ├── sync/             HLC・差分検出・push/pull同期エンジン
│   ├── storage/          SQLite(SQLCipher) アクセス層、マイグレーション、FTS5
│   └── client/           Flutter / CLI / MCP共通のclient/profile・アプリケーションサービス
│
├── cli/                  Rust CLI (clap)。taskveil-client を入口に利用
│
├── mcp-server/           Rust MCP サーバー (rmcp)。taskveil-client を入口に利用
│
├── server/               Rust API サーバー (axum)。AWS Lambda 上で稼働
│   ├── auth/             OPAQUE サーバー実装
│   ├── sync/             push/pull同期API、テナント認可、seq採番
│   └── billing/          IAP / 外部課金プロバイダのWebhook処理
│
└── docs/                 設計ドキュメント
```

- `core/` はcrate群の配置ディレクトリであり、`core`というcrateではない。実packageは`taskveil-client`等、Rust crate名は`taskveil_client`等とする。暗号・同期・ドメインロジックの単一の実装源泉（Single Source of Truth）をこのcrate群へ置く。`core/client`（package `taskveil-client`）はDB open、repository + domain + outbox enqueue、アカウント状態、同期実行をまとめるfrontend非依存の唯一の共通入口とし、Flutter bridgeはFRB公開関数とDTO変換、CLI / MCPは入出力変換に限定する。frontend adapterから下位のcrypto/domain/storage/sync crateへ直接依存しない（2026-07-10改訂: ADR-011、task-91）。
- `server/` は**コントロールプレーン**（認証・ラップ済み鍵の保管・テナント管理・課金Webhook）と**同期データプレーン**（push/pull同期API）を提供する。ただしE2EEデータの中身は一切解釈せず、暗号blobの中継・保管に徹する（§6.1）。ドメインロジック（domain / sync / storage）には依存しないが、OPAQUE等の暗号プロトコル実装を共有するため `core/crypto` には依存しうる（クライアントとサーバーで同一実装系を用い、プロトコル互換を保証するため）。

## 3. データモデル

通常生成するIDは **UUIDv7** を採用する（生成時刻の情報を含み、ソート性とグローバル一意性を両立するため）。例外としてTaskSeriesから生成するtask treeは、series ID、series config revision、occurrence instant、blueprint node keyを入力にしたUUIDv5を用いる。時刻はすべて **UTC epoch milliseconds（int64）** で保持する。以下は論理スキーマであり、実データはレコード単位で暗号化されてサーバーへ同期される（2026-07-24改訂: ADR-024。「4. 暗号設計」「6. 同期プロトコル」参照）。

すべての同期対象エンティティは正確に1つのTenantに属し、Tenantをまたぐ参照は存在しない。AccountとTenantはmembershipによる多対多である。現行releaseはAccount登録時にPersonal Tenantと単一active owner membershipを同じserver transactionで作成する（2026-07-24改訂: ADR-023）。

### 3.5 lists

| フィールド | 型 | 説明 |
|---|---|---|
| id | UUID | リストID |
| name | text（暗号化対象） | リスト名 |
| color | text（暗号化対象） | 表示色 |
| icon | text（暗号化対象） | アイコン識別子 |

ローカルDB（SQLite/SQLCipher）のスキーマバージョンは `PRAGMA user_version` で管理し、`core/storage` のmigration runnerがDB open時に未適用migrationを順次適用する。現行latestはv22である。v17はtask期限をtyped dueへ置換し、v18はactive / completed timer session、local Tenant Root DEK cache、protocol v5同期metadata、v19はcanonical Inbox alias、v20は旧template / schedule、v21はprotocol v7 / envelope v5のTenant Record Key境界、v22はTaskBlueprintを所有する独立Template / TaskSeriesとprotocol v8同期metadataへ切り替える。v22では通常taskを保持して旧recurrence provenanceを外し、暗号化された旧Template / Scheduleを変換せず削除して同期状態を再シードする。旧versionのdual read/writeは行わない（2026-07-24改訂: ADR-017、ADR-018、ADR-021、ADR-023、ADR-024）。

ローカルDB専用のアプリ設定値は、SQLCipher内の `settings` テーブルへ保存する。`settings` は端末ローカルのkey/valueストアであり、ローカルDBファイル全体の保存時暗号化により保護される。Phase 1ではF-01 UIモード保存口として `ui_mode` キーを予約し、未設定時はDart側helperが既定値 `simple` を返す。切替UIと初回選択UIはPhase 3以降のスコープとする（2026-07-08追記: task-63）。同期対象recordには、server ACK済みrevisionとnever-synced creation originを再起動後も識別できる永続状態を持たせ、`base_revision_hlc = null`だけでlocal-newと推測しない（2026-07-11追記: ADR-016）。

| フィールド | 型 | 説明 |
|---|---|---|
| key | TEXT PRIMARY KEY | 設定キー |

期限4列はCHECK constraintで排他的にする。期限なしは全列NULL、日付のみは`due_kind='date'`かつ`due_on`だけ非NULL、日時指定は`due_kind='datetime'`かつ`due_at_ms` / `due_time_zone`だけ非NULLでなければならない。domain / client / FRBはraw epoch単独で期限を公開せず、`Option<TaskDue>`を正本にする。FRB / Dart境界の`TaskDueInput` / `TaskDueDto`は`Date { due_on }` / `DateTime { due_at: DateTime<Utc>, time_zone }`のsealed tagged unionとし、`kind: String` + nullable payloadや`dueAtMs`を公開しない。日付のみは`due_on < viewer_local_today`、日時指定は`now >= due_at`で期限切れとする。Today queryは期限を持つtaskに加え、`scheduled_at`がviewer local todayのtaskを別条件で対象にし、UI分類時も期限なしのscheduled taskをTodayへ残す（2026-07-12追記: ADR-017 / task-101）。

Calendar期間取得は、viewer timezoneから構成したcivil-dateの`[start_on, end_on)`とUTC instantの`[start_at, end_at)`を組にした`CalendarRange`を正本とする。日付のみ期限はcivil-date範囲、日時期限・`scheduled_at`・`completed_at`はinstant範囲で判定し、DST境界で固定24時間を加算しない。`todo` / `in_progress`はdueとscheduledを別occurrenceとして返すため、同一taskが両方を持つ場合は2件になる。`done` / `wont_do`は`completed_at` occurrenceだけを返し、通常agendaとCompletedへ二重表示しない。archive済みlistはlist名とarchive状態を伴って含め、`deleted_at IS NOT NULL`のtaskは除外する。FRB / Dart境界はtyped `CalendarRangeInput`とsealed `CalendarOccurrenceKindDto`（date due / datetime due / scheduled / completed）を用い、task本体とlist contextを返す。occurrenceの日付移動は既存task updateとfield-level LWWへ委譲し、local schema・sync plaintext・protocolを変更しない（2026-07-13追記: task-104）。

`parent_task_id` による自己参照で無制限階層のサブタスクを表現する。ローカル削除は物理削除とし、タスク詳細画面のサブメニューから起動し、不可逆警告の追加確認を必須とする。ゴミ箱は設けず、削除Undoも設けない（完了/編集Undoは維持する）。サブタスクを持つ親タスクを削除する場合は子孫も物理削除する。履歴保全は削除ではなくリストのアーカイブが担う。`tasks.deleted_at` は移行互換のため残置する非推奨列であり、将来のv3マイグレーションで廃止予定である。同期上の削除は`delete_hlc`だけを持ち暗号blobを持たないterminal tagged tombstoneで伝播し、同一record IDのlive復活を許さない（2026-07-11改訂: ADR-010、ADR-014、ADR-016）。

## 4. 暗号設計

本章はE2EE設計の中核であり、最も厳密な実装・レビューを要する領域である。

### 4.1 設計方針

- サーバーはいかなる場合もユーザーのパスワード、および各種コンテンツの平文を保持・観測できない。
- 認証（本人確認）と暗号鍵の保護（Master Keyの保護）は独立した仕組みとし、パスワード変更が発生してもデータ本体の再暗号化を必要としない設計とする。
- Tenantを暗号・membership・同期・local DBの境界とし、ListはTenant内の配置を表す通常の暗号化Recordとする。現行releaseで有効なのはPersonal Tenantとowner membershipだけであり、Shared / Enterprise Tenant、招待、離脱、role別write認可、member向け鍵配送は設計承認までfail closedにする（2026-07-24改訂: ADR-023）。

### 4.2 鍵階層

```text
Password --RFC 9807 OPAQUE--> exportKey --HKDF-SHA256--> KEK_pw --Taskveil wrap v1--> MK
BIP39 24-word entropy --------------------HKDF-SHA256-----------------------> MK
Device Key generation --------------------local capsule wrap----------------> MK
MK --Taskveil wrap v1--> personal Tenant Root DEK generation
Tenant Root DEK --HKDF-SHA256(tenant/generation/collection/record)--> Record Key
Record Key --XChaCha20-Poly1305--> one Record envelope
MK --Taskveil wrap v1--> hybrid Account Root --sign--> per-device certificates
```

テナントごとの **Tenant Root DEK** を唯一のcontent key generationとする。Personal TenantではMKでgeneration別にwrapする。各Record KeyはTenant Root DEKからtenant ID、generation、collection、record IDをdomain-separated inputとしてHKDF-SHA256で導出し、保存・配送しない。List、Task、Tag、Template、Schedule、Timer Session等はすべて同じTenant generationへ属するが、Record identityが異なるため導出鍵は分離される（2026-07-24改訂: ADR-023）。

### 4.3 各鍵の定義

| 鍵 | サイズ/形式 | 生成タイミング | 保存場所 |
|---|---|---|---|
| Device Key (DK) | 32byte 乱数 + generation | 初回起動・端末鍵rotation時 | iOS/macOS: Data Protection Keychain / Android: Keystore sealed capsule / Desktop: OS secret store |
| Master Key (MK) | 32byte 乱数 | アカウント登録時（既存ローカルデータがあればMK配下に移行） | 平文はメモリ上のみ。`wrap(MK, KEK_pw)`をサーバー、`wrap(MK, DK)`をローカル、`wrap(MK, RecoveryKey)`をサーバーに保存 |
| KEK_pw | 32byte（HKDF出力） | ログイン成功（OPAQUE成功）ごとに導出 | 保存しない（都度導出） |
| Recovery Key | BIP39 English 24語、256-bit entropy + checksum、NFKD | アカウント登録・再発行時 | ユーザーのみが保持。phraseを検証して復元したentropyだけをKDFへ入力 |
| Account Root Identity | Ed25519 + ML-DSA-65 | アカウント登録時 | 公開鍵はserver、秘密鍵は`wrap(root SK, MK)`。device certificateを署名 |
| Device Signing / KEM KeyPair | 署名鍵 + X25519 + ML-KEM-768 | device登録・rotation時 | 公開鍵はroot署名certificate、秘密鍵はdevice secret store外へ出さない |
| Tenant Root DEK | 32byte乱数 + generation | tenant作成・除名・侵害・algorithm移行時 | 個人: MKでwrap。Org: 残存deviceごとにhybrid KEMでwrap |
| Record Key | HKDF-SHA256 32byte出力 | Record暗号化・復号時に都度導出 | 保存・配送しない |

端末上ではremote sessionとlocal crypto contextを分離する。すべてのkey wrapはTaskveil namespace v1とし、AADへ固定順のpurpose、user ID、tenant ID、suite ID、generationを該当scopeに応じて含める。`wrap(MK, DK)`はOS secret storeのversioned capsule、Tenant Root DEKはMKでrewrapしてtenant / suite / generationへ束縛する。List単位のkey cache、key bundle、key upload queueは持たない。平文MK / DK / DEK / Record Key / private keyは`Zeroizing` runtime memoryだけに置く。access / refresh token期限切れやnetwork不通でもactive Tenant generationを復元できれば既存dataのmutationを許可するが、必要なactive keyを持たないTenantは同期取得までfail closedにする。匿名利用、旧generation write、pre-Taskveil wrap fallbackは行わない（2026-07-25改訂: ADR-013、ADR-020、ADR-023、ADR-025）。

Taskveil namespace v1の固定値は、HKDF `taskveil/local-db-key/v1`・`taskveil/recovery-key-wrap-key/v1`、key wrap AAD `TWK1`、Apple Keychain `com.taskveil.app.*.v1`、Android Keystore alias `com.taskveil.app.local-capsule-seal.v1`・preferences `taskveil_local_capsules_v1`・AAD `taskveil/android-local-capsule/v1/...`とする。暗号suite、sync protocol、DB schema、capsule plaintext形式は独立したversion空間であり、namespace v1への切替でversion番号を巻き戻さない。

OS secret storeはDK generationとDK-wrapped MKを一体化したcapsuleを`active` / `pending`で保持する。各slotとversioned session credentialはcanonical local profile rootをSHA-256で要約した非秘密namespaceで分離し、別profileのrotation・test・削除や認証状態が本番profileへ作用しないようにする。session credentialはactive token set（access token、refresh token、両期限、issuer / resource origin）または`pending_device_certification` login sagaを単一値として置換する。同一profile配下の個人 / Org tenant DBは同じnamespaceとDKを共有する。DK rotationはpending保存、SQLCipher `PRAGMA rekey`、新DKによる再open検証、active昇格、旧capsule削除の順とする。起動時にpendingが残る場合だけactive / pending双方でDB openを試し、activeならrollback、pendingならcommitを完了する。この二重試行はcrash recovery専用で通常fallbackにしない。Android productionはnon-exportable AES-256-GCM Keystore鍵でcapsuleとsession credentialをsealし、平文`device.key` / `session.token`はdevelopment / test以外で使用しない。Apple platformはData Protection Keychain、`synchronizable=false`、`AfterFirstUnlockThisDeviceOnly`相当を維持する（2026-07-25改訂: ADR-020、ADR-025）。

### 4.4 未登録利用時の扱い

アカウント未登録の状態では、ローカルDBはDevice Keyのみで保護される。アカウント登録時、既存のローカルデータ（個人リスト・タスク等）はMaster Key配下に移行（再暗号化）され、以後DKはMKのラップ用途に限定される。

### 4.5 パスワード変更

パスワード変更時に必要な処理は以下のみである。

1. OPAQUEレジストレーションの再実行（新パスワードでの再登録）。
2. 新しいexportKeyからKEK_pw'を導出し、`wrap(MK, KEK_pw')`を再計算してサーバー側の値を更新。

Master Key自体は不変であるため、**タスク等のデータ本体の再暗号化は一切不要**である。これが、exportKeyを直接Master Keyとして採用せず、間接的にKEK_pwを介してMKをラップする理由である（exportKeyを直接MKとして使うと、パスワード変更のたびに全データの再暗号化が必要になる）。

### 4.6 Shared / Enterprise Tenant

共有境界はListではなくTenantである。ただし現行releaseはPersonal Tenantだけを許可し、Shared / Enterprise Tenantの作成、招待、承諾、離脱、除名、ownership transfer、role別read/write認可、member端末へのTenant Root DEK配送を公開しない。serverの同期認可もPersonal Tenantの単一ownerだけを許可する。

後続のcritical設計ゲートでは、membership状態機械、権限matrix、サーバーが検証するwrite authorization、端末別鍵配送、除名時rotation、offline端末とtombstoneの収束を一体で裁定する。鍵を所持していることだけをwrite権限とみなす暫定共有は導入しない（2026-07-24改訂: ADR-023）。

### 4.7 暗号アルゴリズム・ライブラリ

| 用途 | 方式 | ライブラリ |
|---|---|---|
| 認証 | RFC 9807 OPAQUE、Ristretto255 + 3DH | `opaque-ke >= 4.0.1` |
| パスワードストレッチング（OPAQUE内KSF） | Argon2id 64 MiB / t=3 / p=4 | RustCrypto `argon2` |
| 鍵導出 | HKDF-SHA256 | RustCrypto `hkdf` |

### 4.8 レコード暗号化方式

各エンティティ（task, list, tag, comment等）は、暗号化対象フィールドをまとめたJSONオブジェクトとしてシリアライズし、Tenant Root DEKから当該Record identity用に導出したRecord KeyでXChaCha20-Poly1305暗号化した上でblobとして同期する。

- envelope v5はASCII `TDE5`、suite ID、Tenant key generation、nonce、ciphertextの順である。AADはASCII `TDA5`、suite ID、generation、tenant ID、collection、record IDを固定順で含める。Record KeyのHKDF infoにもtenant ID、generation、collection、record IDを含め、別tenant / collection / record / generationへの暗号文移植を拒否する。旧envelope reader / writerは残さない（2026-07-24改訂: ADR-023）。
- ステータス・優先度・並び順などUI表示上不可欠だが機微性が低いフィールドも、原則としてすべて暗号化対象に含める（サーバー側解析面の最小化を優先する）。同期メタデータとして必要な最小限の情報（後述）のみ平文でサーバーに保持される。

List、Task、Comment、Reminder、Tag、Template、Schedule、Timer Session等の全Recordは所属Tenantのactive Tenant generationを使う。List IDはTask plaintext内の配置であり、key scopeではない。

タスクの同一Tenant内でのList間移動はplacement変更である。record IDとTenant generationが同じため導出Record Keyは変わらず、新しいplaintextを同じRecord Keyで新nonce暗号化して同期する。Tenant間移動は現行releaseでは無効化する。将来有効化する場合も「移動」ではなく、移動先Tenantで新record IDを発行して暗号化するcopyと、移動元recordのdeleteを明示的に組み合わせる。

### 4.9 サーバーが知り得る情報 / 知り得ない情報

**サーバーが知り得る情報**

| 項目 | 内容 |
|---|---|
| アカウントID | ユーザー識別子、メールアドレス |
| OPAQUEレジストレーションレコード | パスワード検証用データ（パスワード自体は含まない） |
| ラップ済み鍵 | generation別のMK / Tenant wrapperとdevice別recipient ciphertext。平文鍵は含まない |
| デバイスリスト | デバイス名、root署名certificate、公開鍵fingerprint、suite、登録/失効日時 |
| 課金状態 | プラン種別、サブスクリプション有効期限 |
| Organizationメンバーシップ | 所属関係、role、Safety verification state、device別wrapped DEK |
| 暗号blob + 同期メタデータ | レコードID、collection種別、revision HLC（ノードID成分を含む）、seq、blobサイズ、サーバー書込み時刻 |

**サーバーが知り得ない情報**

- ユーザーのパスワード（平文はサーバーに一切送信されない）
- タスクのタイトル・メモ・タグ名・コメント本文などのコンテンツ平文
- リマインダー日時、期限日時などの時刻情報（暗号化対象のためサーバーからは不可視）

### 4.10 帰結: プッシュ通知の制約

リマインダー日時はコンテンツとして暗号化されているため、サーバーはリマインド対象・タイミングを把握できず、**サーバー起点のプッシュ通知でリマインドを送信することはできない**。したがって、リマインド通知はすべて**クライアント側のローカルスケジューリング**（OS標準のローカル通知API）によって実現する。この制約により、アプリが完全に終了・OSにより強制停止されている状況での通知信頼性は、プッシュ通知方式に比べて劣る可能性がある点を設計上の既知の制約として明記する。

## 5. ローカルストレージ

### 5.1 採用技術

- ローカルDBは素のSQLite + **SQLCipher** を採用する（Rustからは `rusqlite` の bundled-sqlcipher 系featureを想定）。
- libSQL/Tursoは採用しない（[`05_設計判断記録.md`](./05_設計判断記録.md) ADR-002）。同期はサーバー経由のpush/pull API（6章）であり、クライアントはlibsqlクライアントを持たず、`rusqlite` + SQLCipherと通常のHTTPSクライアントのみを持つ。これにより`rusqlite`+SQLCipherとlibsqlクライアントのSQLite実装二重リンク問題（特にiOS/Androidでのシンボル衝突リスク）も発生しない。
- サーバー（Postgres）に保存されるのはDEKで暗号化済みのblobのみであるため、E2EEの保証はストレージ層の保存時暗号化には依存しない（Postgres側の保存時暗号化を多層防御として有効化してよいが、必須ではない）。
- ローカルDBは**テナントごとにSQLiteファイルを分離**する（個人テナント用ファイル1つ + 所属Orgテナントごとに1ファイル）。SQLCipherの鍵はいずれも5.3節のとおりDevice Key (DK) 由来で共通であり、ファイル分離自体が鍵構造に影響することはない。Org脱退・除名時は当該テナントのファイルを削除するだけで端末上のデータ消去が完結する。FTS5索引もテナントごとのファイル内に閉じる（5.4節参照）。詳細な採用理由は[`05_設計判断記録.md`](./05_設計判断記録.md) ADR-007を参照。

### 5.2 暗号化の2レイヤー構造

「二重暗号化」ではなく、適用場所・脅威モデルの異なる2レイヤーであることを明確にする。

| レイヤー | 方式 | 適用場所 | 脅威モデル |
|---|---|---|---|
| コンテンツ暗号化（E2EE本体） | DEKによるXChaCha20-Poly1305 | 同期境界（push時にblob生成、pull時に復号） | サーバー・ネットワーク上の第三者 |
| 保存時暗号化 | SQLCipher（ページレベル） | ローカルDBファイル全体 | 端末紛失・盗難、他プロセスからのファイル読み取り |

- ローカルDB内のカラムは**平文**で保持する。SQLクエリ・インデックス・ソート・FTS5を機能させるためであり、DEK暗号化されたblobをローカルの正本として保持する設計は採らない。
- DEKによる暗号化は同期境界でのみ適用される。outboxに一時保持される送信待ちblobがSQLCipher内に置かれることはあるが、これは設計上意図した多層であり冗長な二重暗号化ではない。
- local crypto cacheにはPersonal Tenantのactive / migration中Tenant Root DEKだけをMK-wrapped bundleとして保存する。List / Record単位の鍵状態は保存しない。Listを追加・削除してもkey cacheは変化しない（2026-07-24改訂: ADR-023）。
- local schema v13の`sync_quarantine`は、適用不能なremote recordの最新headをrecord ID単位で保持する。保存対象はcollection、server seq、revision HLC、live/tombstone tagとsemantic HLC、live時の暗号blob、型付きreason（`missing_dek` / `no_matching_dek` / `authentication_failed` / `corrupt_envelope` / `invalid_plaintext`）、必要な場合のlist ID、初回/最終失敗時刻、attempt countである。plaintext、DEK、Master Key、session token、crypto libraryの詳細errorは保存しない。record IDに対応するcollectionはrecord state / outbox / quarantine間で不変とし、同seq / revisionの再試行は暗号stateを置換せずattemptだけを加算する。古いseqはlatest headを上書きせず、同seqでrevisionが異なる入力は不正として拒否し、新しいseqだけがheadを置換する。同recordのquarantine中もlocal outbox head自体は保持し、送信列挙だけを停止する。新revisionの適用またはquarantine再適用が成功したtransactionでのみrowを削除する（2026-07-10改訂: ADR-012、task-88）。

### 5.3 ローカルDB鍵

- SQLCipherの鍵は**常にDevice Key (DK) からHKDFで導出**する（登録状態によらず一貫）。
- MK由来の鍵に切り替えない理由: `wrap(MK, DK)` が同一端末に保存される以上、MK由来にしてもDKが破られれば等しく破られるため、防御力が向上しない。鍵を一貫させることでアカウント登録時のDBリキー（PRAGMA rekey）も不要になる。
- 将来オプション（strict mode）: `wrap(MK, DK)` をローカルに保存せず、起動ごとにパスワード入力（OPAQUE）でMKを取得する運用。アプリ起動にパスワードが必須になる代わりに、端末単独ではデータを復号できなくなる。初期リリースのスコープ外とし、12章の未決事項に含める。

### 5.4 全文検索

- FTS5はSQLCipher上でそのまま動作する（SQLCipherはページレベル暗号化のためSQLite機能に透過的である）。
- FTS5の転置インデックスは平文を含むが、暗号化DBファイル内に格納されるため、脅威モデルはレイヤー2（DK保護）に帰着する。
- `tasks_fts` は `tasks` tableの `INSERT` / `UPDATE` / `DELETE` トリガーで同期する。`title` / `note` 更新、移行互換の `deleted_at` 付き行、物理削除はFTS5索引へ即時反映する（2026-07-08追記: task-62）。
- tokenizerは追加依存なしのFTS5標準 `unicode61` を用いる。検索APIは空白区切り語を前方一致queryへ変換するため、英語単語や日本語連続文字列の先頭一致は扱えるが、任意部分一致や日本語の形態素単位分割は提供しない。検索UI設計時はこの制約を前提に、必要ならtokenizer/インデックス設計を再評価する（2026-07-08追記: task-62）。

## 6. 同期プロトコル

現行sync protocolはv8であり、collectionは`lists` / `tasks` / `templates` / `task_series` / `timer_sessions`とする。v8はTemplateとTaskSeriesの独立化、Task provenance変更を伴うbreaking protocolであり、旧`schedules` plaintextとのdual read / writeを行わない。既存record envelope v5、CAS、stable cursor、full-resync、terminal tombstone、quarantineの形式は維持し、protocol version不一致はserver / client双方でfail closedにする（2026-07-24改訂: ADR-024）。

本章の設計判断の経緯は [`05_設計判断記録.md`](./05_設計判断記録.md)（ADR-002〜ADR-005、ADR-010、ADR-012、ADR-014〜ADR-016）を参照。

### 6.1 構成

同期はクライアント⇄サーバー直結ではなく、サーバー（Lambda上のaxum）が提供する**push/pull API**を経由する（ADR-002）。テナント（ユーザーごとの個人テナント、Organizationごとの Orgテナント）は物理DB分離ではなく、単一Postgres内で `tenant_id` により論理分離する（ADR-003）。

論理分離の担保は以下の多層防御による。

- 全クエリに `tenant_id` を必須とするリポジトリ層設計（クエリ条件漏れを型・レビューで検出する）。
- Postgres RLS（Row Level Security）による多層防御。
- 認可の網羅テスト。

認可・課金の有効性検証はAPIリクエストごとにサーバーが実施する。これにより、デバイス失効・課金失効は（旧設計のトークンTTLに伴う遅延なく）即時に同期アクセスへ反映される。

### 6.2 サーバースキーマ

サーバー側Postgresはコンテンツを解釈しない汎用的な同期テーブルのみを保持する。

```sql
CREATE TABLE sync_records (
    tenant_id      UUID    NOT NULL,
    record_id      UUID    NOT NULL,  -- 通常UUIDv7、TaskSeries生成taskはADR-024のUUIDv5
    collection     TEXT    NOT NULL CHECK (collection IN ('lists', 'tasks', 'templates', 'task_series', 'timer_sessions')),
    seq            BIGINT  NOT NULL,  -- pullカーソル用（サーバー到着順）
    revision_hlc   TEXT    NOT NULL,  -- base revision CAS用（固定幅ソート可能エンコード、ノードID内包）
    mutation_hlc   TEXT,              -- live domain変更のsemantic clock
    delete_hlc     TEXT,              -- tombstone削除操作のsemantic clock
    encrypted_blob BYTEA,
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, record_id),
    UNIQUE (tenant_id, seq)
);
CREATE TABLE tenant_seq (tenant_id UUID PRIMARY KEY, last_seq BIGINT NOT NULL);
CREATE TABLE sync_records_history (
    tenant_id UUID NOT NULL, record_id UUID NOT NULL, seq BIGINT NOT NULL,
    collection TEXT NOT NULL, revision_hlc TEXT NOT NULL,
    mutation_hlc TEXT, delete_hlc TEXT, encrypted_blob BYTEA,
    author_user_id UUID NOT NULL, overwritten_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE tenant_device_continuity (
    tenant_id UUID NOT NULL, device_id UUID NOT NULL,
    continuity_seq BIGINT NOT NULL, continuity_generation BIGINT NOT NULL,
    required_generation BIGINT NOT NULL, initialized BOOLEAN NOT NULL,
    PRIMARY KEY (tenant_id, device_id)
);
-- device_resync_sessionsはstable-key base cursorをgeneration単位に保持する。
-- continuity_closure_proofsはproof IDをtenant/device/high-water/generationへ束縛する。
-- live: mutation_hlc + non-empty encrypted_blob、tombstone: delete_hlcのみ。
-- CHECK制約で両stateのnullable shapeと revision_hlc >= semantic clock を強制する。
```

- `sync_records` はレコード（`tenant_id`, `record_id`）ごとに**最新の暗号blobのみ**を保持する（完全append-onlyのopログ方式は不採用。理由はADR-005参照）。
- `seq` はpullカーソル専用であり、「サーバーへの到着順（＝可視になった順）」を表す。`tenant_seq` 行の `UPDATE ... RETURNING` で採番する。この採番は行ロックがコミットまで保持されるため、テナント単位でpushが直列化され「seqの順＝可視になる順」が厳密に保証される（直列化の競合範囲はテナント内、すなわち1ユーザーの数端末〜小規模Orgに限られ実害はない）。
- top-level `revision_hlc` はCAS revision、`mutation_hlc` は最後のdomain/user変更、`delete_hlc` は削除操作を表す。live blobをrevisionの大小だけでblind overwriteせず、pushの`base_revision_hlc`がserver current revisionと一致した場合だけ更新する。stale pushはcurrent envelopeとのclient merge/retryへ戻す（2026-07-10改訂: ADR-012、ADR-014）。
- `sync_records` は `device_id` カラムを持たない。HLCのノードID成分で更新元デバイスの識別は足りており、あえて別カラムを設けないことでメタデータを最小化する（ADR-005）。書き込み主体（ユーザー）の帰属は `sync_records_history.author_user_id` にのみ持たせる。
- `sync_records_history` は上書き時の旧行を退避するテーブルであり、Orgメンバーの破壊的上書きからの復旧手段として30日保持する（詳細は6.6節）。
- tombstone受理時は削除対象の旧contentを`sync_records_history`へ新規退避せず、同record IDの既存historyも削除する。tombstoneには削除伝播に必要なrecord ID、collection、revision / delete clock、seq、時刻以外のcontentを持たせない（2026-07-11追記: ADR-016）。
- `timer_sessions`も同じopaque record table、CAS、continuity、history、terminal tombstoneを使う。serverは暗号blob内のtask ID、mode、実績時間を知らず、初回に受理したlive ciphertextをimmutable headとする。同IDへの異なるlive ciphertextはbaseが一致しても更新せずconflictとして拒否し、exact retryだけをno-opとする（2026-07-13追記: ADR-018、task-105）。
- key generationは`user_key_generations(user_id, generation, suite_id, status, wrapped_mk_by_password, wrapped_mk_by_recovery, wrapper_revision, ...)`、`tenant_key_generations(tenant_id, generation, suite_id, status, signed_manifest, ...)`、Tenant専用の`key_recipients(tenant_id, generation, device_id, recipient_key_fingerprint, wrapped_dek)`へ保存する。Tenant manifestのcanonical payloadは`TKM2`、tenant ID、suite、generation、status、minimum write generation、previous manifest hash、recipient集合からなり、List scope discriminatorやList IDを持たない。statusは`prepared / active / migrating / retired`だけを許し、Tenantごとにactive generationとminimum write generationを単調更新する。`list_key_generations`、`list_key_bundles`、List key APIは持たない（2026-07-24改訂: ADR-023）。
- rotationは`prepared`で残存device bundleを揃え、`active` transactionで新規writeを新世代へ切り替え、`migrating`でlive headだけを再暗号化する。全live head移行、全非expired device continuity ACK、30日history保持終了後にだけ`retired`として旧recipient bundleを削除する。offline端末はactive generation取得まで対象scopeへwriteできない。
- wire上のminimum-write generationはTenant単位で進める。Tenant Root DEK rotationは当該Tenantのlive Recordを新generationのRecord Keyで再暗号化する。List単位rotationは存在しない。manifestはactive manifest hashを指す`prepared`、そのhashを指す`active`の2段階をMK由来HMACで検証し、serverはstatusとhash chainを構造検証する。
- `tenant_device_continuity`、`device_resync_sessions`、`continuity_closure_proofs`はopaqueなtransport continuityだけを保持し、list ID、parent ID、ancestor、aggregate scope / epochを追加しない。closure proofはlocal page / cursorまたはfull-resync rebaseのcommit後にACKされ、そのACK transactionだけが`continuity_seq` / `continuity_generation`を単調更新する（2026-07-11追記: ADR-016、task-98）。
- list tombstoneは暗号blobを持たず再暗号化しない。旧Tenant generationのbundle retirementは、全live headの新generation移行、全非失効deviceのcontinuity ACK、移行完了時点から30日のhistory保持終了を同一transactionで確認した場合だけ成功する。端末失効は`devices.key_expires_at`または`revoked_at`で明示し、単なるofflineやsession期限切れを失効扱いしない（2026-07-24改訂: ADR-020、ADR-023）。

### 6.3 変更追跡

- 各デバイスは **Hybrid Logical Clock (HLC)** を保持し、local mutationとmerge後の再pushでインクリメントする。HLCは「物理時刻（ミリ秒）+ 論理カウンタ + ノードID（デバイス識別子由来）」の3要素からなり、固定幅のソート可能な文字列としてエンコードする。pullでremote revisionをlocal HLCへobserveし、再push revisionは必ず受信revisionより大きくする。observe、採番、HLC永続化、repush用outbox登録は同一local transactionで確定する（2026-07-10改訂: ADR-012）。
- マージはフィールドレベルの **Last-Write-Wins (LWW)** を基本とする。local mutationは実際に変更したfieldのHLCだけを更新し、未変更fieldのHLCを保持する。merge後の再pushもtop-level `revision_hlc` だけを新規採番し、payload内の未変更field HLCを引き上げない（2026-07-10改訂: ADR-012）。
- 暗号blobは`kind=task|list|template|task_series|timer_session`で厳密にtag付けしたcollection別plaintextを持つ。task / listのmutable field groupは`Clocked<T> { value, hlc }`として丸ごと暗号化する。taskは`title`、`note`、`priority`、`due: Option<TaskDue>`、`scheduled_at`、`estimated_minutes`、`assignee`、series provenance、`created_at`、`updated_at`に加え、`completion { status, completed_at, closed_reason }`と`placement { list_id, parent_task_id, rank }`を各1 clockのcompound fieldとして持つ。`due`はtagged union全体へ1 clockを付ける。listは`name`、`color`、`icon`、`is_default`、`archived_at`、`created_at`、`updated_at`と`placement { rank }`を持ち、共有scope fieldを持たない。Template BlueprintとTaskSeries configは各1 atomic field、TaskSeries cursorはconfig revisionへ束縛した単調fieldとする。timer sessionはADR-018の確定実績全体を1つのimmutable valueとして持ち、同ID・異内容をfield mergeしない。未知field、欠落field、collection/kind不一致、live payload内`deleted_at`は受理しない。競合解決情報とtenant-scoped contentは暗号境界内にあり、サーバーからは不可視である（2026-07-24改訂: ADR-012、ADR-014、ADR-017、ADR-018、ADR-023、ADR-024）。
- default Inboxが複数ある場合は、liveかつtyped検証済みで認証済み`is_default=true`のlist sync stateを候補とし、UUID最小のrecordをcanonicalとする。initial pull / full resync closure後も、`collection=lists`のlive current headにunresolved quarantineが1件でもあれば候補集合不明として選挙を保留する。canonicalのpromotion、loserのdemotion、durable alias集合、全既知alias taskのtyped placement更新・Tenant Record Keyでの再暗号化・record state・HLC・outboxを単一`BEGIN IMMEDIATE`で確定し、commit後にだけaliasを非表示にする。通常sync後も冪等に再評価する（2026-07-24改訂: ADR-015、ADR-016、ADR-023）。
- rankは`00000000000000000000000000000000`〜`ffffffffffffffffffffffffffffffff`の固定幅lowercase hex unsigned 128-bitとし、通常挿入は隣接rankの数値中点を使う。taskの表示scopeは`(list_id, parent_task_id)`、listの表示scopeはlocal profile全体で、全経路を`(rank, record_id)`順へ統一する。同rank衝突または隣接値間の空間枯渇時だけ対象scopeを現順のまま十分な間隔へ再配番し、変更されたdomain row、typed field clock、record state、outbox head、local HLCを同一`BEGIN IMMEDIATE`で確定する（2026-07-10改訂: ADR-012、ADR-014）。
- 削除の同期表現は、`state.kind=tombstone`と`delete_hlc`だけを持つtagged stateとする。tombstoneは`encrypted_blob`を持てず、liveは`mutation_hlc`と非空blobを必須とする。liveからtombstoneへのCAS過程ではsemantic clockを用いるが、tombstone受理後の同一record IDに対するtombstone → live遷移はHLCの大小にかかわらず拒否する。再作成は新しいrecord IDを使う（2026-07-11改訂: ADR-010、ADR-012、ADR-014、ADR-016）。
- `seq`、`revision_hlc`、`mutation_hlc` / `delete_hlc`、`field_hlcs` は役割を分離する。`seq` はpull cursor、`revision_hlc` はbase revision CAS、`mutation_hlc` / `delete_hlc` はlive同士のmergeとlive → tombstone遷移のsemantic clock、`field_hlcs` はfield値の競合解決キーである。tombstone受理後のterminal性はclock比較で覆さない（詳細はADR-005、ADR-012、ADR-014、ADR-016）。

### 6.4 同期フロー

1. ローカルでの書込は、domain row、`sync_outbox`、暗号payload生成元となるsync record state、local HLCを共通client層の同一SQLite transactionで確定する。List作成は通常Record作成でありkey stateを追加しない。途中で失敗した場合は全体をrollbackし、local-only / outbox-only commitを作らない（2026-07-24改訂: ADR-011〜ADR-013、ADR-023）。
2. **protocol / continuity / key preflight**: entity outboxを読む前に`GET /v2/tenants/{tenant_id}/preflight`を現行protocol header付きで呼び、responseのprotocol v8、envelope v5、suite ID、Tenantのactive / minimum write generation、signed manifestがclientの対応値と一致することを確認する。unsupported / unsigned / replay / stale generationはSQLCipher設定へdurable blockとして保存し、outbox読取、entity push、payload pull、ACK、cursor更新を行わない。serverは認証済みdeviceのcontinuityと`gc_horizon_seq`を比較し、normal pullかexpired-device full resyncかを裁定する。client申告のcursorだけでpush可否を決めず、旧protocol / generation clientがpreflightを迂回してwrite endpointを直接呼んでも拒否する（2026-07-24改訂: ADR-012、ADR-014、ADR-016〜018、ADR-020、ADR-023、ADR-024）。
3. **pull / delete reconcile**: normal deviceは `GET /v2/tenants/{tenant_id}/pull?since={seq}&limit={n}`、expired deviceはstable-key current-state full resyncを行い、どちらもentity pushより先にremote stateを復号・検証する。pull failureはTenant key不足の`MissingDek`、Record Keyでの`AuthenticationFailed`、既知versionの`CorruptEnvelope` / `InvalidPlaintext`、`UnsupportedEnvelopeVersion`、`UnsupportedProtocolVersion`、既知protocol response不正へ分類する。key不足を検出したpageの初回transactionはcommitせず、network refresh後に同じpage全体を1回だけ再実行する。page内のdomain apply/delete、remote HLC observe、typed record state、merge repush outbox、quarantine upsert/resolve、page末尾cursorを1つのtransactionで確定し、どのwrite failureでも全rollbackする（2026-07-24改訂: ADR-012、ADR-014、ADR-016、ADR-023）。
4. **closure / local rebase**: List tombstoneを受信したclientは、既知Taskを同一Tenantのdefault Inboxへ配置変更してlive Recordとして再pushする。後着Taskが削除済みListを参照する場合もmaterialize前にdefault Inboxへrehomeして再pushする。Task subtree削除などList以外のterminal tombstone規則は維持する。expired-device full resyncではserver current / tombstone / GC済み / never-synced local-newを分類し、dependency closureを検証してlocal rebaseを完了した後にだけclosure proofをACKする（2026-07-24改訂: ADR-016、ADR-023）。
5. **entity push**: clientはdependency順にlocal entity outboxをpushする。`POST /v2/tenants/{tenant_id}/push` は`{op_id, record_id, collection, base_revision_hlc, revision_hlc, state}`を受け取る。`state`は`Live { mutation_hlc, blob }`または`Tombstone { delete_hlc }`である。serverは各pushでdevice continuityを再検証し、expired / old-generation deviceとtombstone済みrecordの`Live`を拒否する。base不一致はcurrent envelope付きconflictとし、clientはmerge/rebase後に再pushする。結果件数、`op_id`、record ID、collectionを照合してからoutboxをACKする（2026-07-24改訂: ADR-014、ADR-016、ADR-023）。
6. マージの結果local値が勝ったfieldがあれば、field HLCと `mutation_hlc` を保持したマージ済みblobを**再push**する。remote revisionをobserveし、それより大きい `revision_hlc` を採番する。tombstone済みの同一record IDはマージ対象にせず、再作成は新IDで行う。push後はecho pullを行う。
7. マージ完了後、ローカルUIへ変更を反映する（リアクティブなクエリ購読を想定）。

初回バックフィルはtenant identityへ結び付いたlocal profileごとに一度だけ実行する。既存local dataを持つprofileを新規tenantへ登録するときは、tenant/profile紐付け後、各recordをnever-synced creation origin付きtransactional seed generationへ登録し、remote current-state scanとclosure後にlist / template / task_series → task → timer sessionの依存順でpushする。TemplateとTaskSeriesの間には依存順を設けない。同一tenantへの再loginだけを理由にcursorやserver-seen stateを削除しない（2026-07-24改訂: ADR-012、ADR-016、ADR-018、ADR-023、ADR-024）。

初回同期およびGC horizon超過後のfull resyncは、厳密な過去snapshotではなくstable-key current-state fuzzy scan + delta catch-upとする。開始transactionで `base_seq` を取得し、base rowを `seq <= base_seq` に限定せずstable keyで走査する。続いて `seq > base_seq` のdeltaを取得し、各delta pageと同じserver transactionで返す `high_water` に `has_more=false` のcursorが到達した時だけclosureとする。expired deviceは未ACK outboxを一律保護せず、server current / server-seen but absent / never-synced local-new / missing dependencyを分類してlocal rebaseを完了する。長期offline中の新規Listはdurable originとlocal-new集合内のdependency closureを検証できれば保護し、List key bundleを要件としない（2026-07-24改訂: ADR-012、ADR-016、ADR-023）。

### 6.5 競合ケースと解決方針

| ケース | 内容 | 解決方針 |
|---|---|---|
| サブタスクの親子同時編集 | デバイスAが親タスクのstatusをdoneに、デバイスBが同じ親の子タスクを新規追加、というように異なるフィールド/異なる階層を同時編集 | 親タスクと子タスクは別レコードのため、レコード単位でのマージにより両方の変更が独立に反映される。親の完了と子の追加は互いを妨げず、UI側で「完了済み親タスクに未完了の子タスクが存在する」状態を許容し警告表示するのみとする |
| 同一タスクのstatus同時更新 | デバイスAがdoneに、デバイスBがin_progressに、ほぼ同時に更新 | フィールドレベルLWWにより、HLCがより新しい方の値を採用する。ユーザー体験上の取りこぼしを避けるため、直近で上書きされた側の変更を「変更履歴」としてローカルに一定期間保持し、必要であれば手動で復元できるようにする（将来拡張。初期リリースではLWWの結果をそのまま採用） |
| 削除と同時編集の競合 | デバイスAがタスクを削除し、デバイスBが同時に当該タスクの内容を編集 | serverがtombstoneを受理した同一record IDはterminal deletionとし、後着の編集HLCが大きくてもliveへ戻さない。編集側は先行pull / rebaseで削除を適用し、stale outboxを破棄する。ユーザーが内容を再作成する場合は新しいrecord IDを発行する（2026-07-11改訂: ADR-016） |
| 同一レコードの異なるフィールドを同時編集 | デバイスAがtitleを、デバイスBがnoteを、同じbaseから編集 | 先着pushだけがbase revision CASに成功する。後着pushはblind overwriteせずcurrent envelope付きconflictとなり、clientがfield mergeして新base/new revisionで再pushする。先着clientがACK直後に停止しても変更は失われない（ADR-014） |

### 6.6 サーバーが強制する不変条件とエッジケース

サーバーはE2EEデータの中身を解釈しない一方で、以下の不変条件をリクエスト単位で強制する（ADR-005）。

- クライアントによるサーバー同期ストアの物理DELETEは不可とし、削除はblobを持たないtagged tombstoneのみで表現する。live/tombstoneの不正なfield組合せはwire deserializeまたはDB CHECK制約で拒否する（2026-07-10改訂: ADR-010、ADR-014）。
- task subtree削除では、削除端末が把握しているrootとdescendantを削除前に列挙し、各recordのtombstoneをdomain物理削除と同じlocal transactionでoutboxへ登録する。List削除は別規則でありTaskを削除しない。既知Taskのplacementをdefault Inboxへ更新しlive Recordとしてenqueueした後、List tombstoneをenqueueする。別端末の後着Taskも削除済みListを検出したclientがdefault Inboxへrehomeして収束させる（2026-07-24改訂: ADR-012、ADR-016、ADR-023）。
- task subtree永久削除では関連する既知timer sessionも削除前に列挙し、session / task tombstone、domain物理削除、record state、outbox、HLCを同じlocal transactionへ含める。List削除ではTask、Reminder、Timer Session、Undo履歴を保持し、Task placementだけを更新する。別端末から遅着したtimer sessionは、復号したtask IDのlocal taskがterminal tombstone済みならmaterializeせずsession tombstoneをenqueueする（2026-07-24改訂: ADR-018、ADR-023）。
- push endpointは、serverが保持するdevice別`continuity_seq` / `continuity_generation`が`gc_horizon_seq`以上の有効世代であることをkey bundle / entityの書込ごとに検証する。expired deviceはserver current-state closureとlocal rebaseが完了するまでpushできない（2026-07-11追記: ADR-016）。
- normal / full-resync pull closureで発行するproofはtenant / device / high-water / generationへ束縛し、別tenant / deviceからのACK、古いgeneration、改変high-waterを拒否する。ACK前の停止ではcontinuityを進めず、同じclosureの再取得と冪等ACKで回復する（2026-07-11追記: ADR-016、task-98）。
- 暗号blobのサイズには上限を設ける（初期値64KB）。
- push/pull 1リクエストあたりのレコード件数（バッチ）にも上限を設ける。
- `collection` はprotocolで列挙した値だけを許可し、既存 `(tenant_id, record_id)` のcollection変更を拒否する。push結果はrequestの順序だけで対応付けず、`op_id`、件数、record IDを検証してからACKする（2026-07-10改訂: ADR-012）。
- pushされたレコードのHLC物理時刻がサーバー時刻より5分を超えて未来である場合、当該pushは拒否する（端末の時計異常や「未来HLCによる永久勝ち」攻撃の抑止のため）。
- 課金の有効性とPersonal Tenantのowner membershipはAPIリクエストごとにサーバー側で検証する。Shared / Enterprise Tenantの同期は後続認可設計が承認されるまで403で拒否する。
- tenant分離の多層防御は、non-owner application role、実際のRLS policy、必要な `FORCE ROW LEVEL SECURITY`、cross-tenant testが揃った状態を指す。`ENABLE ROW LEVEL SECURITY` だけでは完了扱いにしない（2026-07-10改訂: ADR-012）。

エッジケースへの対策は以下のとおりである。

- **Orgメンバーによる破壊的上書き**: 共有リストにおいて悪意ある（または誤操作の）メンバーが他者の変更を意図せず/意図的に上書きした場合に備え、上書き時の旧行を `sync_records_history` へ退避し30日保持する。これにより復旧手段を確保する。
- **tombstone GCとオフライン端末**: tombstoneと通常offline復帰保証は180日とし、GC実行時にテナントごとの `gc_horizon_seq` を単調前進させる。`devices.last_pull_at`やclient申告cursorはGC窓超過判定に使わない。server-trusted continuityがhorizon未満のdeviceはexpiredとし、stable-key fuzzy scan、`base_seq`後delta、high-water closure、server-seen / local-new / dependency closure別のlocal rebaseを完了するまでpushを拒否する。これによりtombstoneを永久保持せず、長期offline中の正当な新規listだけをreseedできる（2026-07-11改訂: ADR-010、ADR-012、ADR-016）。

### 6.7 foreground realtime同期通知

foreground realtime通知は同期protocolの外側にある欠落可能なwake-up hintであり、Postgres current state、HTTPS push / pull、server-trusted continuity、client outbox / cursorが唯一の同期正本である。通知の欠落、重複、順序逆転、provider停止は同期遅延にだけ縮退し、ACK、cursor前進、CAS、merge、GC continuityを変更しない（2026-07-15追記: ADR-019）。

- notification frame v1は`{"v":1,"type":"changed"}`だけを持つ。`high_water`、tenant / device / record識別子、collection、暗号blob、domain plaintextを含めない。
- Cloudflare Worker + tenant単位Durable Objectを初期providerとし、EU jurisdictionのHibernation WebSocket APIを使う。UUID文字列はASCIIの小文字・hyphen付き36文字へ正規化する。tenant channelは`HMAC-SHA256(channel_key, "taskveil-realtime-channel-v1\n" || lowercase_hyphenated_tenant_uuid)`、source device tagは`HMAC-SHA256(channel_key, "taskveil-realtime-device-v1\n" || lowercase_hyphenated_tenant_uuid || "\n" || lowercase_hyphenated_device_uuid)`の32 bytesをbase64url no-paddingした43文字とする。
- clientは認証済み`POST /v2/tenants/{tenant_id}/realtime/ticket`から`{"websocket_url":"wss://.../v1/connect","ticket":"...","expires_at":"RFC3339 UTC"}`を取得する。endpointはsync endpointと同じrequest-time認証・device失効・membership policyを呼び、将来そのpolicyへ課金entitlementを追加した場合も同じ判定を継承する。realtime専用の仮plan判定は追加しない。
- ticket payload bytesは空白なし・field順固定のUTF-8 JSON `{"kid":"<key-id>","aud":"taskveil-realtime","channel":"<43-char>","device":"<43-char>","iat":<unix-seconds>,"exp":<unix-seconds>}`とする。key IDは`[A-Za-z0-9_-]{1,32}`、TTLは300秒である。payload segmentをbase64url no-paddingし、ASCII `taskveil-realtime-ticket-v1\n`とpayload segmentの連結をticket用HMAC-SHA256で署名する。tokenは`<payload-segment>.<base64url-no-padding-signature>`の2 segmentとし、WebSocket Upgradeの`Authorization: Bearer` headerだけで渡す。
- server-to-Worker publish bodyは空白なし・field順固定のUTF-8 JSON `{"v":1,"channel":"<43-char>","source_device":"<43-char>"}`、上限512 bytesとする。`X-Taskveil-Realtime-Key-Id`、Unix秒の`X-Taskveil-Realtime-Timestamp`、base64url no-paddingの`X-Taskveil-Realtime-Signature`を付ける。key IDは検証鍵の選択だけに使い、ASCII `taskveil-realtime-publish-v1\n<timestamp>\n`とraw body bytesの連結をpublish用HMAC-SHA256で署名する。Workerはconstant-timeで検証し、±30秒を超えるrequestを拒否する。accepted push commit後に500ms timeoutでbest effort publishし、失敗してもpush responseを失敗へ戻さない。
- Flutter lifecycle層はsync対象local mutation commit後250msで`TaskveilClient::sync_now`を起動する。single-flight run中のtriggerはdirty flagへまとめ、triggerなしで1 runが完了するまで追従する。remote pull適用後は既存`SyncStatusNotifier`がlist / task / Home / Calendar / search / timer providerをinvalidateし、UI refreshまで完了する。
- foreground / login時だけWebSocketへ接続し、ticketを期限30秒前に更新する。再接続は1〜30秒のexponential backoff + jitter、接続中は5分safety pull、切断中は30秒polling、foreground復帰時は即時syncとする。
- ticket / publish signing keyはcurrent / previous keyによるoverlap rotationを許す。channel derivation keyはv1中固定し、secret、opaque identifier、tenant UUID、device UUIDをpublic logへ出さない。

## 7. アカウントフロー

### 7.1 未登録利用開始

1. アプリ初回起動時、Device Key (DK) を生成しOSキーチェーンへ保存。
2. DK由来の鍵でローカルDB（SQLite + SQLCipher）を初期化・暗号化。
3. アカウント登録なしでリスト・タスクの作成/編集がフル機能で可能（同期・共有・課金プランに紐づく上位機能を除く）。

### 7.2 新規登録（既存ローカルデータの移行を含む）

1. メールアドレス・パスワードを入力し、クライアントでOPAQUEレジストレーションを実行（パスワードはサーバーへ非送信）。
2. exportKeyからHKDFでKEK_pwを導出。
3. Master Key (MK) を新規生成。
4. 既存ローカルデータ（DK配下で暗号化済み）をMK配下へ再暗号化して移行。
5. `wrap(MK, KEK_pw)` と `wrap(MK, DK)` を生成し、それぞれサーバー・ローカルに保存。
6. Recovery Keyを生成し、`wrap(MK, RecoveryKey)` をサーバーに保存。Recovery Key自体はユーザーに提示し、安全な場所への保管を促す（サーバー・端末には平文を残さない）。
7. Ed25519 + ML-DSA-65 account rootを生成し、root秘密鍵をMKでwrapする。device signing / X25519 + ML-KEM-768鍵は端末secret storeで生成し、server challengeへのproof-of-possession後にroot署名device certificateを登録する。
8. サーバー側でPostgres内にテナントレコードを作成する。サインアップフローにはリージョン選択のステップが含まれる（初期はデータレジデンシー未対応のため選択肢は1つのみ。[`05_設計判断記録.md`](./05_設計判断記録.md) ADR-006参照）。
9. 認証完了時に15分有効のopaque Bearer access tokenとローテーション式refresh tokenを発行する。OPAQUE `export_key`は端末内のMK解除だけに使用し、tokenへ導出しない。

### 7.3 ログイン・新デバイス追加

1. 新デバイスでメールアドレス・パスワードを入力し、OPAQUEログインを実行。
2. exportKeyからKEK_pwを導出し、サーバーから取得した `wrap(MK, KEK_pw)` を復号してMKを得る。
3. MKでaccount root秘密鍵を復号し、新端末がlocal secret storeで生成したdevice signing / hybrid KEM公開鍵へcertificateを署名する。
4. 新デバイスのDK generation 1 capsuleをactiveとして保存し、server challengeへのproof-of-possessionとdevice certificateを登録する。device秘密鍵は端末secret store外へ出さない。
5. 端末certificate登録後にaccess tokenで同期API（6章）のstable-key fuzzy scan + delta full resyncを実行し、ローカルDBを構築。

### 7.4 セッション管理

- access tokenは32 byte乱数のopaque Bearer tokenで最大15分かつsession family absolute期限以内とし、resource endpointへだけ送る。serverはSHA-256 hashだけを保存し、token、session family、device certificate / key期限、tenant membership、課金をrequestごとに検証する。
- refresh tokenは32 byte乱数のopaque tokenで、`POST /v1/auth/token`へ`application/x-www-form-urlencoded`の`grant_type=refresh_token`、`client_id=taskveil-native`として送る。public clientのためclient secretは使用しない。idle期限は30日、family absolute期限は90日である。
- refreshは同一DB transactionで旧tokenを消費し、新しいaccess / refresh pairを発行する。消費済みrefresh tokenの再利用を検知した場合はfamily rowをO(1)で失効し、配下tokenを即時無効化する。grace windowは設けず、応答喪失時は再loginする。consumed tokenはreuse検知のためfamily absolute期限まで保持する。認証・refresh request時の期限切れaccess token、期限切れfamily配下token、空family、期限切れprovisional device、OPAQUE state回収は段階的な固定上限batchとし、未認証requestへ無制限DELETE / UPDATE / cascadeを負わせない。
- token setはaccess / refresh token、各期限、正規化済みissuer / resource originを一体保存する。production originはHTTPS必須、localhost / loopbackだけHTTPを許可し、refresh、sync、revokeをtoken側originへ固定する。activeまたはpending credential中は別originへの設定変更を拒否する。
- clientはaccess期限60秒前にrefreshする。loginはOPAQUE finish後のprovisional sessionをlocal profileへ照合し、device秘密identity、enrollment proof、key material、origin-bound tokenをOS安全領域の`pending_device_certification`へ保存してからcertifyする。provisional deviceはcertificate / `certified_at`が揃うまでresource、refresh、roster、key recipient、rotation ACK対象外である。certifyは同一certificateの再試行を冪等にし、成功後のlocal finalizeでactive token setを最後に公開する。crash / 保存失敗はpendingから再開し、identity不一致または未認証challenge期限切れはremote revoke後に破棄する。local pending保存前のcrashでもprovisionalはactive stateをblockせず期限後にbounded cleanupされる。
- register / login、refresh、logout、起動復元・期限切れ削除は同一local profileのcross-process advisory lockで直列化する。別processがcredential更新中なら旧refresh tokenを送らずbusyとする。長時間実行されるsync / realtime resource requestが401の場合は強制refresh後に一度だけ再試行する。refresh不能時はremote sessionだけをlogged-outとし、local crypto contextとoffline dataは保持する。
- logoutはRFC 7009互換の`POST /v1/auth/revoke`へrefresh tokenを渡し、family全体を失効する。未知tokenにも200を返す。clientはremoteの200を確認してからlocal credentialを削除し、network / timeout / 非2xxではcredentialを保持して失敗を返すため、logoutはonline-requiredである。RFC 8414 metadataは`GET /.well-known/oauth-authorization-server`でissuer、token endpoint、revocation endpoint、対応grant / client authentication methodを公開する。
- DPoPは導入しない。access token窃取時は最大15分replay可能であるため、安全領域保存、TLS、ログ禁止、短命化、refresh rotation、request-time検証でriskを制限する（2026-07-25改訂: ADR-025）。

### 7.5 パスワード変更

1. 現在のパスワードでOPAQUE認証し、MKを取得済みの状態にする。
2. 新パスワードでOPAQUEレジストレーションを再実行。
3. 新exportKeyからKEK_pw'を導出し、`wrap(MK, KEK_pw')` を再計算してサーバー側の値を更新。
4. データ本体の再暗号化は不要（4.5節参照）。

### 7.6 リカバリーキーでの復旧

1. パスワードを忘れた場合、ユーザーが保管しているRecovery Keyを入力。
2. サーバーから `wrap(MK, RecoveryKey)` を取得し、Recovery KeyでMKを復号。
3. MKが得られたら、新しいパスワードを設定しOPAQUE再登録を実行、`wrap(MK, KEK_pw_new)` を生成してサーバーへ保存。
4. 新しいRecovery Keyを再発行し、旧Recovery Keyを無効化（サーバー側の `wrap(MK, RecoveryKey)` を新しい値で上書き）。

### 7.7 デバイス失効

1. ユーザーが既存デバイス一覧から対象デバイスを選択し失効操作を実行。
2. account rootで次の`device_roster_revision`と現在chain head hashを含む`TDR1`失効statementへhybrid署名し、serverは署名・certificate fingerprint・revision / previous hash CASを検証して `devices.revoked_at` とstatementを同一transactionで保存する。対象accountが所属する全Organizationを同じtransactionでrotation-requiredにする。同期API（push/pull）はリクエストごとに `devices.revoked_at` を検証するため、**失効は即時に実効化される**（旧設計のような発行済みトークンのTTL経過待ちは発生せず、失効反映の遅延はない）。
3. Personal Tenantは必要に応じてTenant Root DEKの新generationを発行し、失効deviceをrecipient集合から除外してlive headを移行する。Shared / Enterprise Tenantの除名rotationは共有設計ゲートまで有効化しない。失効前に取得済みの鍵・plaintextは遠隔消去できない。

## 8. MCP / CLI

### 8.1 共通方針

CLIおよびMCPサーバーは、いずれもfrontend共通入口の`taskveil-client` crateにある`TaskveilClient`を通じてローカルの暗号化DBへ直接アクセスし、**サーバーAPIを経由しない**。`TaskveilClient::open`へはDB directoryとbootstrap値だけを持つ`LocalProfileConfig`を渡す。これにより、オフライン環境でもCLI/MCP双方がフル機能で動作し、同期は`taskveil-client`のcoordinatorが`taskveil-sync`のstate machineを用いて非同期に処理する。crate境界の詳細は[`dev/client-profile-architecture.md`](./dev/client-profile-architecture.md)を参照する（2026-07-10改訂: task-91、task-94）。

Windows / macOS / Linuxでは、同一PC上のFlutterデスクトップ版、CLI、MCPサーバーが同じTaskveil local profile（SQLCipher DB + OS secret store上のDevice Key参照）を共有する。異なるPCやOS間でDBファイルやDevice Keyをコピーせず、各端末のprofile間はE2EE同期で収束させる（ADR-011）。

OS別の本番secret storeは、macOSが同一Apple Team / Keychain access groupのData Protection Keychain、Windowsがcurrent-user scopeのDPAPI、LinuxがSecret Service APIとする。Windows / Linuxでは平文 `device.key` fallbackを開発・テスト用途に限定し、Secret Service等が利用できない場合に本番CLIが平文保存へ自動降格してはならない。

同一DBへの多重process接続では、connectionごとの `busy_timeout`、短い書込transaction、migration排他を必須とする。domain更新と同期outbox登録は同一transactionで確定し、同期runはDB-backed lease等で同一profileにつき1つへ制限する。

### 8.2 MCPサーバー

- トランスポートは **stdio** を採用する（ローカルプロセス間通信であり、ネットワーク経由でのE2EEデータ露出を避けるため）。
- 提供するtoolsの例:

| tool名 | 概要 |
|---|---|
| `list_tasks` | 指定リスト・条件（status、期限等）でタスク一覧を取得 |
| `create_task` | 新規タスクを作成（親タスク指定によるサブタスク作成も可） |
| `complete_task` | タスクを完了状態に更新 |
| `search_tasks` | 全文検索（ローカルFTS5インデックス経由） |

- 初回のtool呼び出し時、ローカルDBへのアクセスに対するユーザーの明示的な許可プロンプトを表示し、以後のセッションでの利用可否を確認する。

### 8.3 CLI

Rustバイナリとして `clap` を用いてサブコマンド体系を構築する。

```
taskveil add "牛乳を買う" --due tomorrow
taskveil add "資料作成" --list work --priority 2 --parent <task-id>
taskveil list --list work --status todo
taskveil done <task-id>
taskveil search "牛乳"
```

CLI・MCPサーバーともに、初回起動時に対象アカウントのローカルDB（未登録時はDK保護のローカルのみのDB、登録済みならMK保護のDB）へ接続するための鍵取得フロー（OSキーチェーンからのDK取得、必要であればパスワード入力によるMK取得）を実行する。

macOS CLIはFlutter appと同じKeychain access groupを持つ署名済みバイナリとして配布する。Windows CLIは同一WindowsユーザーのDPAPI保護secret、Linux CLIは同一ログインセッションのSecret Service itemを取得する。profile / data-dirを明示指定できる場合もDevice Keyを引数、環境変数、ログへ露出してはならない。

## 9. ローカルAI

### 9.1 方針

推論は**オンデバイスのみ**で実行し、タスク内容がサーバーはもとより外部のAI APIへ送信されることも一切ない。これによりE2EEの前提（サーバーがコンテンツを知り得ない）をAI機能導入後も維持する。

### 9.2 実装

- 推論エンジンには llama.cpp系のRustバインディング、または `candle` を用いる。
- モデルはGGUF量子化形式、2〜4Bパラメータクラスの軽量モデルを対象とし、ユーザーが任意のタイミングでダウンロード・削除できるモデル管理UIを提供する（初期状態ではモデル未同梱とし、アプリサイズの肥大化を避ける）。

### 9.3 対応機能

| 機能 | 概要 |
|---|---|
| 自然言語パース | 「明日の15時に資料作成」のような自然文からタイトル・期限・リストを抽出しタスク化 |
| タスク分解 | 大きなタスクをサブタスクの候補に分解して提案 |
| 週次要約 | 完了/未完了タスクの傾向をローカルで要約しレポート表示 |

### 9.4 低スペック端末フォールバック

推論に必要な最低メモリ/CPU要件を満たさない端末では、AI機能そのものをUI上非表示にし、モデルダウンロードや推論呼び出しを行わないようにする。判定は端末のRAM容量・CPUコア数等の静的情報に基づき、アプリ起動時に一度だけ実施する。

## 10. 課金・プラン制御

本章は概要である。公開向けの課金方針は `billing_overview.md` を参照する。具体価格、収益試算、provider別の運用判断はprivate repo側で管理する。

### 10.1 プラン体系

Free / Pro / Org の3プランを設け、機能をプラン単位でゲートする。

- **Free**: ローカルで完結する全機能（リスト・タスク・タグ・リマインダー・テンプレート・スケジュール自動起票・タイマー・統計・ローカルAI・CLI/MCP を含む）。単一端末利用。同期・共有は不可。
- **Pro**: E2EE同期（マルチデバイス）、暗号化クラウドバックアップ。
- **Org**: Organization共有、担当者アサイン・コメント、メンバー管理、監査ログ。

機能ゲートはサーバー依存機能（同期・共有）に限定され、ローカル機能はプランによらず制限しない。

### 10.2 実装方針

- iOS / Android実装はRevenueCatをprovider adapterとして使用する。buildは`TASKVEIL_REVENUECAT_IOS_API_KEY` / `TASKVEIL_REVENUECAT_ANDROID_API_KEY`のうち実行platform専用のpublic SDK keyと`TASKVEIL_REVENUECAT_ENVIRONMENT`を受け取り、serverが返す課金環境と不一致なら初期化を拒否する。購入、復元、storeが返すsubscription管理URLは両mobile platformで同じclient境界を使い、desktopではprovider課金を初期化しない。client SDKの表示やreceiptを認可の正本にせず、serverがRevenueCat APIから再取得したsubscription snapshotを`account_entitlements`へ集約する。`users.plan`のような第二の課金状態は持たない。
- クライアントはサーバーから取得した機能フラグに従いUI上の機能出し分けを行う。フラグの正当性はサーバー起点であり、クライアント側での改ざんに対しては、機能ゲートが必要な操作（例: Org作成、同期API（push/pull）へのアクセス）についてはサーバー側APIでリクエストごとに再検証する（6.1節参照）。トークン発行時点の一括判定ではなく、リクエスト単位の検証であるため課金失効は同期アクセスへ即時に反映される。
- エンタイトルメント判定の唯一の真実は自社serverの`account_entitlements`とし、RevenueCatはその更新sourceとして抽象化する。初回状態は`free / trial / active / grace / expired / revoked`、同期許可は`trial / active / grace`だけとする。Apple Billing Grace Periodは16日とし、独自のgrace期限を重ねない。

### 10.3 課金失効時の挙動

課金が失効（サブスクリプション解約・支払い失敗等）した場合でも、**ローカルデータは全機能で編集を継続できる**ものとする。失効により制限されるのはサーバーとの同期（およびOrg共有等のサーバー依存機能）のみであり、ユーザーのデータそのものを人質に取らない方針を明確にする。同期停止中に行われたローカル変更は、再度課金が有効化された時点で通常のpush/pullフローにより同期される。

### 10.4 一般リリースゲート

最初の一般リリースは、iOS App Store / Android Google Playの購入・復元、server-side receipt / transaction / event検証、冪等なsubscription集約、エンタイトルメント取得、同期APIのrequest-time認可、失効・返金・再有効化を各store sandboxでend-to-end検証した後に行う。課金基盤が未完了の間はstore提出、release tag、公開告知を行わない。クライアント表示だけのplan判定、未検証receipt、固定の開発用entitlementはゲート合格の証拠として扱わない。

## 11. テスト・品質

### 11.1 Rustコア

- **暗号処理**: RFC 9807 OPAQUE、BIP39、HKDF、XChaCha20-Poly1305、FIPS 203 ML-KEM-768、FIPS 204 ML-DSA-65について公式 / 参照実装test vector、wrong password / checksum / AAD / generation / suiteを整備する。envelope / manifest / certificate / identity parser fuzzは16 KiB以上を扱い、ML-DSA / ML-KEMを含む4 KiB超のwire shapeを除外しない。direct crypto / platform dependencyのexact pin確認と、tracked / untracked fileの秘密情報grepもrelease gateに含める。
- **同期エンジン**: property testと2-client統合testはproduction CRUD / common client経路を通す。異field同時編集、remote revision observe、terminal tombstone済みrecordの同一ID復活拒否、List削除時のTask rehome、task/list reorder、placement原子性、rank衝突、local write/outbox/record-state/HLC/cursor各crash window、missing Tenant DEK / corrupt blobのdurable quarantine、unknown protocolのupgrade-required、push response照合を自動テストする（2026-07-24改訂: ADR-012、ADR-016、ADR-023）。
- **フル再同期 / GC**: 新規tenantへのnever-synced seed、server-trusted continuityがexpiredの場合のentity push拒否、server-seen but absent recordの破棄、長期offline中の新規listとtaskの保護、missing/deleted dependencyの除外、空server、resync中の同時更新、stable-key fuzzy scan、`base_seq` 後deltaとpage transactionのhigh-water closureを自動テストする（2026-07-24改訂: ADR-010、ADR-012、ADR-016、ADR-023）。

### 11.2 Flutter

- 主要画面のwidget testと、実DBを用いたシナリオベースのintegration test（タスク作成〜同期〜他デバイス反映等）を整備する。

### 11.3 脆弱性対応

- 依存クレートの脆弱性監査に `cargo audit --deny warnings` をCIパイプラインへ組み込み、脆弱性、unmaintained、unsound、yanked dependencyを定期的（週次等）にfail closedで検出する。
- E2EE設計・実装は、一般リリース前に実装担当と独立した暗号reviewを必須とする。外部第三者reviewが完了するまで「監査済み」と表示しない。監査範囲には鍵階層、OPAQUE、Recovery、rotation、device certificate、hybrid PQC共有、server保存dataの解析可能性を含める（ADR-020）。
